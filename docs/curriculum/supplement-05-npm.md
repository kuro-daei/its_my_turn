## 1. Node.js と npm の関係

### Node.js とは

**結論から言うと、Node.js は「JavaScript をウェブブラウザの外で動かすための実行環境」です。**

> **Node.js（ノードジェイエス）とは？** もともと JavaScript はウェブブラウザの中だけで動く言語でした。Node.js はその JavaScript を、ブラウザを使わずにパソコン（サーバー）上で直接動かせるようにした仕組みです。「JavaScript のための実行エンジン」と考えるとイメージしやすいです。

このカリキュラムで使う Next.js というフレームワークは、JavaScript で書かれています。Next.js を動かすには、パソコンに Node.js がインストールされている必要があります。

### npm とは

**npm とは、Node.js に標準で付属するパッケージ管理ツールです。**

> **npm（エヌピーエム）とは？** 「Node Package Manager」の略で、Node.js のパッケージ（部品）を管理するツールです。Node.js をインストールすると、自動的に一緒にインストールされます。

> **パッケージとは？** 他の開発者が作って公開した「再利用可能なプログラムの部品」です。「認証機能」「デザインコンポーネント」「日付の計算ライブラリ」など、よく使われる機能が世界中の開発者によってパッケージとして公開されています。自分でゼロから作る必要なく、これらを取り込んで使えます。

**たとえ話:** Node.js をスマートフォン本体とすると、npm はアプリストア（App Store / Google Play）です。スマートフォン本体（Node.js）がなければアプリ（パッケージ）は動きません。アプリストア（npm）を通じて、世界中で公開されているアプリ（パッケージ）を手元にインストールして使えます。「地図アプリを入れよう」「カメラアプリを追加しよう」と同じ感覚で、開発に必要な部品を追加できます。

### Node.js と npm の関係まとめ

| | 役割 | たとえ |
|--|------|--------|
| **Node.js** | JavaScript を動かす実行環境 | スマートフォン本体 |
| **npm** | パッケージを管理するツール | アプリストア |
| **パッケージ** | 公開された部品・ライブラリ | ダウンロードしたアプリ |

## 2. package.json とは

### package.json の役割

**package.json は、そのプロジェクトの「設計書」です。**

> **package.json とは？** プロジェクトのルートフォルダにある JSON ファイルです。「このプロジェクトの名前・バージョン」「使用しているパッケージの一覧」「実行できるコマンドの定義」などが記録されています。npm はこのファイルを読んで、必要なパッケージをインストールしたり、コマンドを実行したりします。

**たとえ話:** package.json は「建物の設計書兼仕様書」のようなものです。「この建物に使われている材料（パッケージ）の一覧」と「管理コマンド（電気を入れる手順、換気する手順など）」がまとめて書かれています。新しい人がこのプロジェクトに参加したとき、package.json を見るだけで「何が使われているか・何ができるか」を把握できます。

### よく出てくる項目

実際の package.json の例と、各項目の意味を確認します。

```text
# output
{
  "name": "my-todo-app",
  "version": "0.1.0",
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "next start"
  },
  "dependencies": {
    "next": "15.0.0",
    "react": "18.3.0"
  },
  "devDependencies": {
    "typescript": "5.6.0"
  }
}
```

#### `name` と `version`

| 項目 | 説明 |
|------|------|
| `name` | プロジェクトの名前 |
| `version` | プロジェクトのバージョン（`0.1.0` のように数字で表す） |

#### `scripts` — 実行できるコマンドの定義

`scripts` に書かれた項目が、`npm run ○○` で呼び出せるコマンドです。

| スクリプト名 | 実際に実行されるコマンド | 意味 |
|------------|----------------------|------|
| `dev` | `next dev` | 開発サーバーを起動する |
| `build` | `next build` | 本番用にビルドする |
| `start` | `next start` | ビルド済みアプリを起動する |

`npm run dev` は「`scripts` の中の `dev` を実行して」という意味です。

#### `dependencies` と `devDependencies`

| 項目 | 説明 | 例 |
|------|------|----|
| `dependencies` | アプリの動作に必要なパッケージ | `next`、`react`（本番環境でも使う） |
| `devDependencies` | 開発時だけ必要なパッケージ | `typescript`、テストツールなど（開発中だけ使う） |

> **`devDependencies` とは？** 開発中の作業を助けるツール（型チェック・テスト・コードのフォーマットなど）は、アプリの完成品（本番環境）には不要です。こうした「開発中だけ使うパッケージ」を `devDependencies` に分けることで、本番環境を軽くできます。

### `node_modules` フォルダとは

`npm install` を実行すると、プロジェクトフォルダの中に `node_modules` というフォルダが作られます。ここに、インストールしたすべてのパッケージの実体が保存されます。

> **`node_modules` とは？** npm がダウンロードしたパッケージをすべて格納するフォルダです。中身は非常に大きく（数万ファイル、数百 MB になることもある）、package.json さえあれば `npm install` でいつでも再生成できます。

**`node_modules` は Git で管理しません。** 理由は 2 つあります。

1. **サイズが大きすぎる** — 数万ファイルを Git で管理するとリポジトリが肥大化する
2. **再現性がある** — package.json（と package-lock.json）さえ Git にあれば、`npm install` 一発で同じ内容を再生成できる

そのため、`.gitignore` に `node_modules/` が記載されており、GitHub にはアップロードされません。他の人からプロジェクトを受け取ったとき、まず `npm install` を実行するのはこのためです。

## 3. よく使うコマンド集

### コマンド一覧

| コマンド | 何をするか | いつ使うか |
|---------|-----------|-----------|
| `npm install` | package.json に書かれた全パッケージをインストールする | プロジェクトを初めてセットアップするとき |
| `npm install パッケージ名` | 特定のパッケージを追加インストールする | 新しいライブラリを使いたいとき |
| `npm run dev` | 開発サーバーを起動する | 手元でアプリを確認したいとき |
| `npm run build` | 本番用にビルドする | デプロイ前の最終確認・Vercel へのデプロイ時 |
| `npm run start` | ビルド済みのアプリを起動する | ビルド結果を手元で確認したいとき |
| `npx コマンド名` | インストールせず一時的にコマンドを実行する | プロジェクトを新規作成するときなど |

### 各コマンドの詳細

#### `npm install`

```bash
# bash
npm install
```

package.json の `dependencies` と `devDependencies` に書かれているすべてのパッケージを、一括でインストールします。インストールされた内容は `node_modules` フォルダに格納されます。

**使うタイミング:**

- プロジェクトを GitHub からクローン（コピー）してきた直後
- 他の人がパッケージを追加した後、自分の環境に反映するとき
- `node_modules` を削除してやり直したいとき

#### `npm install パッケージ名`

```bash
# bash
npm install @supabase/supabase-js
```

特定のパッケージを新たに追加します。実行すると package.json の `dependencies` に自動で追記されます。

#### `npm run dev`

```bash
# bash
npm run dev
```

開発サーバーを起動します。実行後、ブラウザで `http://localhost:3000` を開くとアプリの画面が確認できます。ファイルを保存するたびに自動で画面が更新されます（ホットリロード）。

> **localhost（ローカルホスト）とは？** 自分のパソコンの中だけで動いているサーバーのアドレスです。`localhost:3000` は「自分のパソコンの 3000 番ポートで動いているサーバー」を指します。インターネットに公開されているわけではなく、自分だけが見られる状態です。

#### `npm run build`

```bash
# bash
npm run build
```

アプリを本番環境向けに最適化・変換します。圧縮・最適化された実行ファイル群が `.next` フォルダに生成されます。**開発中は通過していたエラーも、ここで厳格にチェックされます**（詳細はセクション 4 で解説）。

#### `npm run start`

```bash
# bash
npm run start
```

`npm run build` で生成したビルド済みアプリを起動します。本番と同じ状態でローカルに確認したいときに使います。必ず `npm run build` の後に実行してください。

### `npm` と `npx` の違い

`npx` は「パッケージをインストールせずに一時的に実行するツール」です。

| | `npm` | `npx` |
|--|-------|-------|
| **主な用途** | パッケージのインストール・スクリプトの実行 | コマンドの一時実行 |
| **インストール** | パッケージを `node_modules` に保存する | 保存せず一時的に使う |
| **使い方** | `npm install ○○` / `npm run ○○` | `npx ○○` |

**たとえ話:** `npm install` が「アプリをスマートフォンにダウンロードしてインストールすること」なら、`npx` は「インストールせずにウェブ上で一時的に使うこと」です。

#### `npx create-next-app` がなぜ `npx` を使うのか

```bash
# bash
npx create-next-app@latest my-todo-app
```

`create-next-app` は「新しい Next.js プロジェクトを作るためのツール」です。プロジェクトを作ったら、その後は使いません。毎回インストールして最新版を保つより、`npx` で「最新版をその場で一時実行」する方が合理的です。

これが `npm install create-next-app` ではなく `npx create-next-app` を使う理由です。

## 4. `npm run dev` と `npm run build` の違い

非エンジニアが最も混乱しやすいポイントを整理します。

### 何が違うのか

| | `npm run dev` | `npm run build` |
|--|--------------|-----------------|
| **用途** | 開発中の動作確認 | 本番公開の準備 |
| **速度** | 速く起動するが最適化はしない | 最適化・圧縮に時間がかかる |
| **エラーチェック** | 緩め（一部のエラーは見逃す） | 厳格（型エラーも全部チェックする） |
| **出力先** | メモリ上（ファイルに保存しない） | `.next` フォルダ |
| **使うタイミング** | 手元で動作確認したいとき | Vercel にデプロイする前 |

### 「開発中は通っていたのにビルドで失敗する」のはなぜか

これはよくある困惑ポイントです。答えは「開発モードは意図的に厳しさを抑えているから」です。

**たとえ話:** `npm run dev` は「下書きの原稿チェック」です。大まかな内容が伝わればよく、誤字や細かい表現はひとまず見逃してくれます。一方 `npm run build` は「出版前の最終校正」です。誤字・脱字・文法ミスが 1 か所でもあれば、そのまま出版（デプロイ）させてくれません。

具体的には、`npm run build` では TypeScript の型エラーも例外なく全部チェックされます。開発モードでは「まあ動くからいいか」と流してくれていたものが、ビルドでは「これはルール違反です」と止められます。

**対処法:**

ビルドに失敗したら、Claude Code にそのエラーメッセージをそのまま貼り付けて「ビルドエラーを直してください」と依頼してください。Claude Code がエラーを読んで修正してくれます。

```bash
# bash
npm run build
# エラーが出た場合、そのメッセージをコピーして Claude Code に渡す
```

## 6. まとめ — クイックリファレンス

### インストール・セットアップ

```bash
# bash
# プロジェクトの全パッケージをインストールする（初回 or 環境リセット後）
npm install

# 特定のパッケージを追加する
npm install パッケージ名

# 新しい Next.js プロジェクトを作成する
npx create-next-app@latest プロジェクト名
```

### 開発・確認

```bash
# bash
# 開発サーバーを起動する（http://localhost:3000 で確認できる）
npm run dev

# 本番用ビルドを実行する（デプロイ前の必須確認）
npm run build

# ビルド済みアプリをローカルで起動する（ビルド後に実行）
npm run start
```

### コマンドの選び方

| やりたいこと | 使うコマンド |
|------------|------------|
| 手元でアプリを確認したい | `npm run dev` |
| Vercel にデプロイする前に確認したい | `npm run build` |
| 新しいライブラリを使いたい | `npm install ライブラリ名` |
| 新しいプロジェクトを作りたい | `npx create-next-app@latest` |
| `node_modules` を作り直したい | `node_modules` を削除して `npm install` |

### 用語の早見表

| 用語 | 一言で言うと |
|------|------------|
| **Node.js** | JavaScript をパソコン上で動かす実行環境 |
| **npm** | パッケージを管理するアプリストア |
| **パッケージ** | 公開されている再利用可能な部品 |
| **package.json** | プロジェクトの設計書・仕様書 |
| **node_modules** | インストールされたパッケージの保管場所（Git 管理外） |
| **npm run dev** | 開発用サーバーを起動する（緩めのチェック） |
| **npm run build** | 本番用に最適化・変換する（厳格なチェック） |
| **npx** | インストールせず一時的にコマンドを実行する |

> **覚えておきたい一文:** 「開発中は `npm run dev`、デプロイ前は `npm run build`」——この 2 つの使い分けさえ押さえれば、カリキュラムを通じて困ることはありません。
