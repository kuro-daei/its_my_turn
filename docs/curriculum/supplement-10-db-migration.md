## 1. マイグレーションとは — まず結論から

**マイグレーション（migration）とは、データベースの構造変更を記録したファイルです。**

データベースに新しいテーブルを追加したり、列を変更したりするとき、その「変更手順」を SQL ファイルに書き残しておく仕組みをマイグレーションと呼びます。

> [!NOTE]
> **SQL（エスキューエル）とは？** データベースへの命令を書くための言語です。「このテーブルを作って」「この列を追加して」「このデータを取得して」といった命令を、決まった文法で書きます。

「なぜそんなものが必要なの？」と感じるかもしれません。まずはたとえ話で直感的に理解しましょう。

---

## 2. なぜマイグレーションが必要なのか — たとえ話で理解する

### 直接書き換えてしまうと何が困るか

データベースを直接書き換えることを「手術台でいきなりメスを入れる」ことに例えてみましょう。

外科手術では、**必ず術前記録を残します。** 「何を、どの順番で、どのように処置したか」を記録することで、後から「あの操作は正しかったか」を確認できます。逆に記録なしに手術してしまうと、問題が起きたとき何が原因かわからず、元に戻すこともできません。

データベースの変更も同じです。

**たとえ話: 引っ越し業者の作業手順書**

マイグレーションは「引っ越し業者の作業手順書」のようなものです。

- 「まずタンスを 3 階から運ぶ」「次にベッドを解体する」「最後に荷物をトラックに積む」という手順を書いた指示書
- この手順書があれば、**別の業者でも同じ順番で同じ作業を再現できます**
- 「あのとき何をどの順番でやったか」を後から確認できます
- もし途中でミスがあっても、どのステップで起きたかを特定できます

データベースでも同様に、「このテーブルを作った」「この列を追加した」「このインデックスを追加した」という変更の記録があれば、**別の環境でも全く同じ構造のデータベースを再現できます。**

### 複数の環境がある現実

アプリ開発には複数の環境があります。

| 環境 | 用途 |
|------|------|
| **ローカル環境** | 自分のパソコンで開発・テストする |
| **本番環境** | 実際のユーザーが使う |

「ローカルで動いたのに本番で動かない」という問題の多くは、**環境によってデータベースの構造が違う**ことが原因です。マイグレーションファイルがあれば、どの環境でも同じ手順で同じ構造を作れるため、この問題を防げます。

### データが入った本番環境での変更

もう一つ重要な理由があります。本番環境には**実際のユーザーデータが入っています。**

テーブルごと消して作り直すわけにはいきません。「今のデータを壊さずに、テーブルの構造だけ変更する」という手術のような操作が必要です。マイグレーションはこの操作を安全に行うための仕組みです。

## 3. Supabase でのマイグレーションの仕組み

### `supabase/migrations/` フォルダ

Supabase プロジェクトのフォルダ構成には、`supabase/migrations/` というフォルダがあります。

```text
your-app/
├── supabase/
│   ├── migrations/
│   │   ├── 20240101000000_create_todos.sql   ← マイグレーションファイル
│   │   └── 20240115000000_add_priority.sql   ← 後から追加した変更
│   └── config.toml
├── src/
└── ...
```

このフォルダ内の `.sql` ファイルが「変更の手順書」です。

### ファイル名の命名規則

マイグレーションファイルの名前は、次の形式になっています。

```text
YYYYMMDDHHMMSS_変更の内容.sql
20240101000000_create_todos.sql
  ↑
  作成日時（タイムスタンプ）
```

先頭のタイムスタンプ（日時）が重要です。Supabase はこのタイムスタンプ順にファイルを実行します。「先に `todos` テーブルを作ってから、その後で列を追加する」という**実行順序を保証する**ためです。

### SQL ファイルの中身

マイグレーションファイルの中身は SQL で書かれた「データベースへの命令」です。

```sql
-- 20240101000000_create_todos.sql
CREATE TABLE todos (
    id uuid DEFAULT gen_random_uuid() PRIMARY KEY,
    user_id uuid REFERENCES auth.users NOT NULL,
    title text NOT NULL,
    is_done boolean DEFAULT false,
    created_at timestamptz DEFAULT now()
);

ALTER TABLE todos ENABLE ROW LEVEL SECURITY;
```

> [!NOTE]
> **SQL の読み方（ざっくり）:** `CREATE TABLE` は「テーブルを作る」、`ALTER TABLE` は「テーブルを変更する」という命令です。ここでは「todos というテーブルを作り、RLS（行レベルセキュリティ）を有効にする」という命令が書かれています。

このファイルが「変更の手順書」として機能します。

## 4. Claude Code がマイグレーションをどう扱うか

### Claude Code が自動で SQL を生成する

Chapter 4 の Vibe Coding では、Claude Code に「TODO アプリのデータベースを作って」と指示するだけで、Claude Code が自動的にマイグレーションファイルを生成します。

つまり、**あなたが SQL を書く必要はありません。**

Claude Code が行うこと:

1. 「どんなテーブルが必要か」を考える
2. 必要な SQL を自動生成する
3. タイムスタンプ付きのファイル名で `supabase/migrations/` フォルダに保存する

### MCP 経由で DB を操作する

Claude Code は MCP（Model Context Protocol）という仕組みを通じて、Supabase のデータベースと直接やり取りできます。

> [!NOTE]
> **MCP とは？** Claude Code が外部ツールやサービスと連携するための「接続口」です。API と似た概念で、Claude Code がデータベースの構造を確認したり、変更を適用したりするときに使います。

MCP を使うことで、Claude Code は次のことができます:

- 現在のデータベースの構造を確認する
- 「何を変更すべきか」を判断する
- マイグレーションファイルを生成してあなたに提示する

ただし、**実際にデータベースへ変更を適用するのはあなた自身です。** Claude Code が生成したファイルを確認してから、コマンドで実行するという流れになります。

## 5. マイグレーションを実行する流れ

### 全体の流れ

```text
┌─────────────────────────────────────────────────────┐
│           マイグレーションの流れ                      │
│                                                     │
│  1. Claude Code がマイグレーションファイルを生成       │
│     supabase/migrations/YYYYMMDDHHMMSS_xxx.sql       │
│                          ↓                          │
│  2. あなたがファイルの内容を確認する                   │
│                          ↓                          │
│  3. supabase db push でデータベースへ適用する          │
│                          ↓                          │
│  4. Supabase ダッシュボードで変更を確認する            │
└─────────────────────────────────────────────────────┘
```

### `supabase db push` コマンド

`supabase db push` は「マイグレーションファイルをデータベースへ適用する」コマンドです。

```bash
supabase db push
```

このコマンドを実行すると、Supabase が次の処理を行います。

1. `supabase/migrations/` フォルダ内のファイルをタイムスタンプ順に並べる
2. まだ適用していないファイルだけを実行する
3. 実行済みのファイルは二度と実行しない（重複適用を防ぐ）

「まだ実行していないものだけを実行する」という仕組みがポイントです。同じ変更が二重に適用されて、データが壊れることを防いでいます。

### よく使うコマンド一覧

| コマンド | 内容 |
|---------|------|
| `supabase db push` | ローカルのマイグレーションをリモートの Supabase に適用する |
| `supabase db pull` | リモートの Supabase の構造をローカルに同期する |
| `supabase migration list` | どのマイグレーションが適用済みかを一覧表示する |
| `supabase db reset` | ローカルの開発用 DB をリセットして全マイグレーションを再実行する（ローカルのみ） |

> [!WARNING]
> **注意:** `supabase db reset` はローカルの開発用データベースのみリセットします。本番環境に影響を与えることはありません。

## 6. よくあるトラブルと対処

### トラブル 1: 「マイグレーションが競合している」

**症状**: `supabase db push` を実行したとき、「conflict」や「already exists」というエラーが出る。

**原因**: すでにデータベースに存在するテーブルや列を、再び作ろうとしている。

**対処**: マイグレーションファイルの内容を確認し、`CREATE TABLE IF NOT EXISTS`（テーブルが存在しなければ作る）のように条件付きの記述に変更する。または、Claude Code に「このエラーが出た。マイグレーションを修正して」と伝えると自動で修正してくれます。

```sql
-- 修正前（エラーになることがある）
CREATE TABLE todos (...);

-- 修正後（安全）
CREATE TABLE IF NOT EXISTS todos (...);
```

### トラブル 2: 「ローカルと本番の構造がずれている」

**症状**: ローカルでは動くのに、Vercel にデプロイすると動かない。

**原因**: ローカルの `supabase db push` を忘れており、本番環境のデータベース構造がローカルと違う。

**対処**: `supabase migration list` で適用状況を確認し、`supabase db push` で本番にも変更を適用する。

```bash
# 適用状況を確認する
supabase migration list

# 本番環境に適用する
supabase db push
```

### トラブル 3: ロールバック（変更を元に戻したい）

**症状**: マイグレーションを適用したが、問題が発生したので元に戻したい。

**Supabase の基本的な考え方**: 適用済みのマイグレーションは「元に戻す」のではなく、**「元に戻す処理を行う新しいマイグレーションを追加する」** という方法を取ります。

**たとえ話:** 引っ越し手順書で「タンスを 3 階に運んだ」という作業を取り消したいとき、手順書に「タンスを 3 階から下ろす」という新しい手順を追加するイメージです。過去の手順書を書き換えるのではなく、**新しい作業指示を追加する** という方向です。

具体的には「元に戻す SQL」を書いた新しいマイグレーションファイルを作成します。

```sql
-- 例: テーブルを追加したマイグレーションを元に戻す場合
DROP TABLE IF EXISTS todos;
```

> [!WARNING]
> **注意:** `DROP TABLE` はテーブルとその中のデータを全削除します。本番環境で実行するときは、データのバックアップを必ず取ってから行ってください。

### トラブル 4: 「どのマイグレーションが適用済みかわからない」

**対処**: `supabase migration list` コマンドで確認できます。

```bash
supabase migration list
```

```text
# output
  LOCAL                           │ REMOTE                         │ TIME (UTC)
  ─────────────────────────────── │ ────────────────────────────── │ ──────────────────────
  20240101000000_create_todos     │ 20240101000000_create_todos     │ 2024-01-01 00:00:00
  20240115000000_add_priority     │ 20240115000000_add_priority     │ 2024-01-15 00:00:00
  20240201000000_add_tags         │                                 │
```

`REMOTE` 欄が空欄のものは、まだ本番に適用されていないマイグレーションです。

## 7. まとめ

この補足資料で解説した内容を整理します。

```text
マイグレーションの全体像

  ┌──────────────────────────────────────────────────┐
  │            Claude Code（あなたの AI 相棒）         │
  │  「todos テーブルを作って」という指示を受けて       │
  │  マイグレーションファイルを自動生成する             │
  └────────────────────┬─────────────────────────────┘
                       │ supabase/migrations/ に保存
                       ▼
  ┌──────────────────────────────────────────────────┐
  │           マイグレーションファイル                 │
  │  20240101000000_create_todos.sql                 │
  │  「こういう順番でこういう変更をする」という手順書   │
  └────────────────────┬─────────────────────────────┘
                       │ supabase db push で適用
                       ▼
  ┌──────────────────────────────────────────────────┐
  │           Supabase データベース（本番）             │
  │  変更が安全に適用される                            │
  │  適用済みの記録が残るため、二重適用は起きない       │
  └──────────────────────────────────────────────────┘
```

重要なポイントを 3 つにまとめます。

1. **マイグレーションはデータベース変更の「手順書」** — 「何をどの順番で変更したか」を SQL ファイルに記録することで、どの環境でも同じ構造を再現できます

2. **Claude Code が自動で生成してくれる** — あなたが SQL を書く必要はありません。「このテーブルが必要」と伝えれば、Claude Code が適切なマイグレーションファイルを作ります

3. **`supabase db push` で適用、適用済みは二度と実行しない** — Supabase が「どのマイグレーションが適用済みか」を管理しているため、重複適用によるデータ破損を防いでいます

> [!IMPORTANT]
> **覚えておきたい一文:** マイグレーションとは「データベースの変更を安全に記録・再現するための手順書」です。Claude Code が自動で作ってくれるため、あなたが意識することは「変更を確認して `supabase db push` で適用する」だけです。
