## 1. Git とは — たとえ話で全体像をつかむ

Git は**プロジェクトの「変更履歴」をまるごと管理するツール**です。

> **たとえ話:** 大切な書類を何度も書き直すとき、「最終版.docx」「最終版2.docx」「本当の最終版.docx」と名前を変えて保存した経験はありませんか？ Git はこの「版管理」を自動で、きちんと行ってくれます。「いつ・誰が・何を・なぜ変えたか」がすべて記録に残り、「3 日前の状態に戻したい」も 1 コマンドで実現できます。

Git を使うと、以下のことが実現できます。

- 変更を記録しておき、いつでも過去の状態に戻せる
- 「別の机」を用意して、実験的な変更を本体に影響させずに試せる
- 変更履歴をチームで共有し、誰が何をしたか追跡できる
- 「この修正はどのタスクのためか」を紐付けて管理できる

このカリキュラムでは Claude Code が Git 操作をほとんど自動で行います。あなたがやるのは「こういう変更をして」と指示することだけです。

## 2. 基本用語集

### リポジトリ（Repository）

> **リポジトリとは？** プロジェクトのファイル全体と、その変更履歴をまるごと保存する「倉庫」です。`git init` というコマンドを実行するか、GitHub でリポジトリを作成すると生まれます。Chapter 1 で作ったプロジェクトフォルダは、すでにリポジトリになっています。

リポジトリには 2 種類あります。

| 種類 | 場所 | 説明 |
|------|------|------|
| **ローカルリポジトリ** | 自分の PC | 手元で作業する場所 |
| **リモートリポジトリ** | GitHub（クラウド） | 共有・バックアップ・公開の場所 |

**たとえ話:** ローカルが「自分の作業デスク」、リモート（GitHub）が「オフィスの共有棚」です。デスクで仕上げた書類を共有棚に置く操作が「プッシュ」、共有棚から最新の書類を取ってくる操作が「プル」にあたります。

---

### ブランチ（Branch）

> **ブランチとは？** 同じプロジェクトの「写し」を作って、別々に作業できる仕組みです。実験や修正を「本体」に影響させずに進められます。

**たとえ話:** 大切な書類のコピーを 1 部取って、そのコピーに書き込む、というイメージです。コピーに何を書いても元の書類は汚れません。完成したら元の書類に反映（マージ）します。

Git の基本的な構成：

```text
main ブランチ（本体・常に安全な状態）
  │
  ├── feat_google_auth（作業用コピー A）
  │
  └── fix_issue_3（作業用コピー B）
```

このカリキュラムでは `main` ブランチが「本体」で、作業は必ず別のブランチで行います。Claude Code が `claude -w` で自動的にブランチを作成してくれます。

---

### コミット（Commit）

> **コミットとは？** 変更内容をスナップショット（写真）として記録する操作です。「どんな変更を・いつ・なぜ行ったか」がメッセージとともに残ります。

**たとえ話:** 書類の「決定稿」を日付とコメントを添えて保存する操作です。スナップショットは積み重なっていくため、「5 回前の決定稿に戻したい」が可能になります。

コミットには**コミットメッセージ**がつきます。このカリキュラムでは Conventional Commits という形式を使います。

```text
feat: Google ログインを実装する (#1)
 ↑     ↑                        ↑
種類   何をしたか              関連 Issue 番号
```

よく使う種類の一覧：

| プレフィックス | 意味 |
|--------------|------|
| `feat:` | 新機能の追加 |
| `fix:` | バグ修正 |
| `docs:` | ドキュメントの変更 |
| `chore:` | 設定変更・依存パッケージ更新など |

> **コミットメッセージに `(#番号)` を書く理由:** GitHub が自動でコミットと Issue を紐付けてくれます。後から「この変更はどのタスクのためだったか」がすぐわかります。

---

### マージ（Merge）

> **マージとは？** ブランチで行った変更を、本体（main ブランチ）に取り込む操作です。

**たとえ話:** コピーの書類に書き込んだ内容を、元の書類に転記する操作です。転記が完了したらコピーは不要になります（ブランチを削除）。

マージには方式がいくつかあります。このカリキュラムでは通常の `--merge` 方式を使います。

| 方式 | 特徴 | 使う場面 |
|------|------|---------|
| `--merge` | コミット履歴がそのまま残る | このカリキュラムの標準 |
| `--squash` | 複数のコミットを 1 つにまとめてマージ | コミット数を整理したい場合 |
| `--rebase` | 履歴を直線的に整理してマージ | 上級者向け |

---

### プッシュ / プル（Push / Pull）

> **プッシュとは？** 手元（ローカル）の変更をリモート（GitHub）に送る操作です。
>
> **プルとは？** リモート（GitHub）の最新状態を手元（ローカル）に取り込む操作です。

**たとえ話:** プッシュは「作業デスクの書類を共有棚に置く」、プルは「共有棚から最新の書類を取ってくる」操作です。

Claude Code が `git push` を実行すると、GitHub 上のリポジトリにも変更が反映されます。PR を作るためには、まずプッシュが必要です。

---

### PR（プルリクエスト）

> **PR（プルリクエスト）とは？** 「このブランチの変更を main に取り込んでいいですか？」という申請です。レビュー（確認）の場としても機能します。

**たとえ話:** コピーに書き込んだ内容を「元の書類に反映していいですか？」と確認するプロセスです。一人で作業する場合でも、「どんな変更をしたか」の記録として PR を残す習慣がおすすめです。

PR に書く `Closes #番号` という記述は、マージ時に関連する Issue を自動でクローズします。

```text
Closes #1
 ↑      ↑
魔法の言葉  クローズする Issue 番号
```

## 3. GitHub Issues — タスクを記録する仕組み

GitHub Issues は、「やること・バグ・気になること」を記録する仕組みです。

> **たとえ話:** 仕事で使う付箋や、タスク管理ツールの「チケット」をイメージしてください。「ボタンの色が地味」「ログイン画面でエラーが出た」といった小さな気づきから、「Google ログインを実装する」といった大きなタスクまで、すべて Issue に残しておきます。Issue には番号が自動でつくため、コミットや PR と紐付けて追跡できます。

### Issue の構成要素

| 要素 | 説明 | 例 |
|------|------|----|
| **タイトル** | 何をするか一言で | `feat: Google ログインを実装する` |
| **本文** | 詳細・背景・完了条件など | 実装の目的や手順 |
| **ラベル** | 種類の分類 | `bug`, `enhancement`, `documentation` |
| **担当者（Assignee）** | 誰がやるか | 一人に絞るのがベスト |
| **マイルストーン** | リリース目標への紐付け | 上級者向け |

> **完了条件を書く習慣:** 「何ができたら完了か」を本文に書いておくと、後から「これで終わりだっけ？」と迷わずにすみます。

### Issue の作り方（Claude Code から）

Claude Code に指示するだけで Issue を作れます。

```plaintext
GitHub に Issue を立てて。タイトルは「feat: Google ログインを実装する」、内容は「Supabase Auth で Google ログインを実装する」にして
```

Claude Code が自動で実行するコマンド:

```bash
gh issue create \
  --title "feat: Google ログインを実装する" \
  --body "Supabase Auth で Google ログインを実装する"
```

> **`gh` コマンドとは？** GitHub 公式のコマンドラインツール（GitHub CLI）です。Issue や PR をターミナルから操作できます。Claude Code が自動で使うため、自分で打つ必要はほとんどありません。

### Issue とコミット・PR の紐付け

コミットメッセージや PR 本文に番号を書くと、GitHub が自動でリンクを張ってくれます。

**コミットメッセージに `(#番号)` を書く場合:**

```text
feat: Google ログインを実装する (#1)
                                 ↑
                         Issue #1 と紐付く
```

**PR 本文に `Closes #番号` を書く場合:**

```text
Closes #1
 ↑      ↑
魔法の言葉  クローズする Issue 番号
（PR マージ時に Issue が自動でクローズされる）
```

> **`Closes #番号` とは？** PR 本文にこの一文を書くと、PR がマージされた瞬間に対応する Issue が自動でクローズ（完了）されます。手動でクローズし忘れる心配がなくなります。

### よく使うコマンド

```bash
# Issue を一覧表示する
gh issue list

# クローズ済みの Issue を見る
gh issue list --state closed

# Issue の詳細を見る
gh issue view 1
```

### Issue 管理のベストプラクティス

1. **「思いついたらすぐ記録」の習慣** — 小さな気づきもすぐ Issue に残す
2. **1 Issue = 1 タスク** — 複数のやることを 1 つの Issue に詰め込まない
3. **完了条件を書く** — 「何ができたら完了か」を本文に書いておく
4. **コミット・PR に必ず番号を付ける** — `(#番号)` でリンクが自動生成される
5. **マージしたら Issue をクローズする** — `Closes #番号` を PR に書けば自動でクローズされる

## 4. ブランチ戦略（GitHub Flow）

このカリキュラムでは **GitHub Flow** というブランチ戦略を採用しています。シンプルで、個人・小規模チームに最適なルールです。

### ルールの全体像

```text
① main ブランチは常に「動作する状態」に保つ
② 作業は必ず feature ブランチで行う
③ 完成したら PR を出してマージする
④ マージしたブランチはすぐ削除する
```

> **main ブランチを守る理由:** main ブランチは「いつでも動く状態の本体」です。直接修正すると、壊れた状態が本体に残ってしまいます。必ず「別の机（ブランチ）」で作業して、確認してから取り込む習慣が、安全な開発の基本です。

### ブランチの命名規則

| パターン | 意味 | 例 |
|---------|------|----|
| `feat_機能名` | 新機能の追加 | `feat_google_auth` |
| `fix_issue_番号` | Issue 対応の修正 | `fix_issue_3` |
| `docs_説明` | ドキュメント修正 | `docs_readme` |

Claude Code が `claude -w 名前` で起動すると、この命名規則に沿ったブランチが自動で作成されます。

## 5. Git Worktree 詳細

### Worktree とは

> **Worktree（ワークツリー）とは？** 1 つのリポジトリに対して「複数の机」を同時に用意できる仕組みです。各机は独立したブランチで動作し、互いに影響しません。

**たとえ話:** 1 つの書類棚（リポジトリ）を共有しながら、2 台の机（ワークツリー）でそれぞれ別の書類に取り組んでいるイメージです。A の机での作業が B の机に影響することはありません。

通常の Git では「ブランチを切り替える（`git checkout`）」ことで別の作業に移ります。この場合、同時に複数のブランチを開いて作業することはできません。Worktree を使うと、**複数のブランチを同時に別のフォルダで開いて作業できます**。

```text
【Worktree なし】
プロジェクトフォルダ
  └── 現在いるブランチ（1 つのみ）

【Worktree あり】
プロジェクトフォルダ（main ブランチ）
  │
  └── .claude/worktrees/
        ├── feat_google_auth/（feat_google_auth ブランチ）
        └── fix_issue_3/（fix_issue_3 ブランチ）
```

### Claude Code との組み合わせ

`claude -w 名前` を実行すると、以下が一括で行われます。

1. `feat_名前` という名前のブランチを作成する
2. そのブランチ用の Worktree フォルダを作成する
3. そのフォルダで Claude Code のセッションを開始する

```bash
# このコマンド 1 行で「新しい机の用意」と「その机での作業開始」が完了する
claude -w feat_google_auth
```

> **Claude Code と Worktree の相性がいい理由:** AI エージェントは「今どのブランチにいるか」を常に把握して作業します。Worktree で独立したフォルダを用意することで、複数の修正タスクを並行させても混線しません。「この Claude Code セッションはこの机専用」が明確になります。

### 主要コマンド

Worktree を直接操作する場面は少ないですが、トラブルシュートのために覚えておくと便利です。

```bash
# 一覧を確認する（現在いる Worktree がわかる）
git worktree list

# 削除する（PR マージ後に実行）
git worktree remove .claude/worktrees/feat_google_auth

# 古い参照を整理する（定期メンテナンス）
git worktree prune
```

> **`git worktree add` について:** Worktree を手動で作成するコマンドですが、このカリキュラムでは `claude -w` が代わりに自動で実行します。自分で打つ必要はありません。

### 片付けの手順

PR をマージしたら、使い終わった Worktree を必ず片付けます。

```bash
# Step 1: Worktree フォルダを削除する
git worktree remove .claude/worktrees/feat_google_auth

# Step 2: ブランチも削除する
git branch -d feat_google_auth

# Step 3: 片付いたか確認する
git worktree list
```

期待される出力（main のみ残っている状態）：

```text
/home/yourname/myproject  abc1234 [main]
```

### Worktree のベストプラクティス

**1. タスクがわかる名前をつける**

`feat_google_auth`、`fix_issue_3` のように、「何のための作業か」が名前を見てわかるようにします。`temp` や `test` のような曖昧な名前は避けてください。

**2. アクティブなタスクのみ作成する**

作業が終わっていないタスクの分だけ Worktree を作ります。「後で使うかも」と残しておくと、どれが現在進行中かわからなくなります。

**3. マージしたらすぐ片付ける**

PR をマージしたその日のうちに `git worktree remove` → `git branch -d` を実行します。「後で片付ける」は積み重なります。

**4. 定期的に prune する**

`git worktree prune` を時々実行して古い参照を整理します。`claude -w` がうまく動かないときの最初の対処としても有効です。

### 注意点

- **同じブランチを複数の Worktree で同時に使うことはできません。** `feat_google_auth` の Worktree が存在するとき、同じブランチ名で `claude -w feat_google_auth` を実行すると既存の Worktree が使われます（新規作成されません）。
- **未コミットの変更があると `git worktree remove` が失敗します。** 「変更が残っているけど削除したい」場合は `--force` オプションで強制削除できますが、変更内容が消えるので注意してください。
- **`.claude/worktrees/` フォルダは Claude Code が自動管理します。** 直接ファイルを触ったり手動で削除したりしないでください。

## 6. コマンドリファレンス

Claude Code が自動で実行するコマンドの一覧です。「Claude Code が何をやっているか」を確認したいときに参照してください。

### 状態確認

```bash
# 現在いるブランチを確認する
git branch --show-current

# コミット履歴を確認する
git log --oneline

# ファイルの変更状態を確認する
git status

# Worktree の一覧を確認する
git worktree list
```

### ブランチ操作

```bash
# ブランチを作成して移動する
git checkout -b feat_google_auth

# 別のブランチに移動する
git checkout main

# ブランチを削除する（マージ済みのみ）
git branch -d feat_google_auth
```

### コミット操作

```bash
# 変更をすべてステージに追加する
git add .

# コミットする
git commit -m "feat: Google ログインを実装する (#1)"

# コミットメッセージを修正する（push 前のみ）
git commit --amend -m "feat: 正しいメッセージ (#1)"
```

### リモート操作（GitHub 連携）

```bash
# リモートに push する
git push -u origin feat_google_auth

# リモートから最新を取り込む
git pull origin main
```

### Issue / PR 操作（GitHub CLI）

```bash
# Issue の一覧を確認する
gh issue list

# PR の一覧を確認する
gh pr list

# PR の差分を確認する
gh pr diff 2

# PR をマージする
gh pr merge 2 --merge
```

### Worktree 操作

```bash
# Worktree の一覧を確認する
git worktree list

# Worktree を削除する
git worktree remove .claude/worktrees/feat_google_auth

# 古い参照を整理する
git worktree prune
```

## 7. まとめ

この補足資料で解説した概念を、ひとつの流れで整理します。

```text
1. Issue を立てる
   → やることを GitHub に記録する（タスク管理）

2. Worktree（別の机）を作る
   → claude -w feat_xxx で本体に影響しない作業場所を用意する

3. ブランチで作業してコミットする
   → 変更のスナップショットを「何を・なぜ変えたか」とともに記録する

4. Push して PR を出す
   → 変更をリモート（GitHub）に送り、「取り込んでいいですか？」と申請する

5. レビューしてマージする
   → 意図した変更かを確認して、main ブランチに取り込む

6. 片付ける
   → 使い終わった Worktree とブランチを削除してクリーンな状態に戻す
```

このサイクルを回すことで、アプリが安全に、着実に育っていきます。

> **覚えておきたい一文:** Git と Worktree の仕組みがあるから、Claude Code は「本体を壊さずに実験して、確認してから取り込む」を自動でやってくれています。コマンドを暗記する必要はありません。「何をやっているか」がわかれば十分です。
