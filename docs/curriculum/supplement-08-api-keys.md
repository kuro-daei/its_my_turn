# 補足 8: API キーの安全な扱い方 — 「見せてよいキー」と「絶対に隠すキー」

**種別**: 概念解説＋実践ガイド（ハイブリッド）
**関連チャプター**: Chapter 3「Supabase 初期設定」、Chapter 6「Vercel デプロイ」

---

## この記事を読むとわかること

- なぜ API キーに「公開してよいもの」と「絶対に隠すもの」があるのか
- フロントエンドのコードが危険な理由
- このカリキュラムで登場するキーをどう扱うべきか

「キーを GitHub に上げてしまった」「本番環境で設定を間違えた」——こうしたミスは、初心者に限らずベテランのエンジニアにも起きます。この記事では、明日から実践できる「キーの安全な扱い方」を体系的に解説します。

---

## 結論：キーには 2 種類ある

API キーには大きく分けて **2 種類** あります。

| 種類 | フロントエンドに置けるか | 理由 |
|------|------------------------|------|
| **公開してよいキー** | 置ける（条件付き） | 漏れても被害が最小限になるよう設計されている |
| **絶対に隠すキー** | 置けない | 漏れると DB の全データにアクセスされる |

重要なのは「漏れたら困るかどうか」ではなく、**「そのキーが持つ権限の強さ」**です。権限が強いキーほど、漏れたときの被害が大きくなります。

---

## たとえ話：オフィスのゲスト用 IC カードとマスターキー

大きなオフィスビルを想像してください。来客者には「ゲスト用 IC カード」が渡されます。このカードでは、エントランスと会議室にしか入れません。受付、倉庫、サーバールームには入れないようになっています。

一方、施設管理者だけが持つ「マスターキー」は、ビル内のすべての扉を開けられます。会議室も、サーバールームも、金庫室も例外なく。

このたとえ話で整理すると、

- **publishable key（パブリッシャブルキー）** = ゲスト用 IC カード。入れる場所（権限）が最初から限られている。万が一コピーされても、入れる範囲が限定的なのでダメージが小さい
- **service_role key（サービスロールキー）** = マスターキー。すべての扉を開けられる。絶対に第三者に渡してはいけない
- **RLS（Row Level Security）** = セキュリティゲート。ゲストカードで入れる部屋をさらに細かく制限する仕組み

ゲスト用 IC カードを渡すことは問題ありません。ただし、「ゲストカードではここには入れない」というゲートが正しく設定されていることが前提です。これが **RLS が必須である理由**です。

> **publishable key とは？** 「公開可能なキー」の意。Supabase が発行するキーのうち、アプリのフロントエンドで使うことを想定した公開キーです。RLS が有効な状態では、このキーでアクセスできる範囲はルールで厳しく制限されます。
>
> **service_role key とは？** Supabase が発行する管理者用のキーです。RLS を完全にバイパス（無効化）して、データベースのすべてのデータにアクセスできます。サーバーサイドの処理専用であり、フロントエンドに置くことは絶対に禁止です。
>
> **RLS（Row Level Security）とは？** データベースの「行レベルのセキュリティ」機能です。「自分のデータしか読めない」「ログインしていないと書き込めない」といったルールを、データベース側で強制します。RLS が無効だと、publishable key でも全データにアクセスできてしまいます。

## フロントエンドとサーバーサイドの違い

### フロントエンドのコードは「誰でも読める」

アプリのフロントエンドとは、ブラウザ上で動く部分です。ユーザーが見ている画面、ボタン、フォームはすべてフロントエンドです。

フロントエンドのコードは、ブラウザを通じてユーザーの手元に届きます。つまり、**誰でも読むことができます。**

ブラウザで「右クリック → ページのソースを表示」を押すか、開発者ツール（F12）を開くと、フロントエンドのコードがそのまま表示されます。難読化（読みにくくする処理）をしても、解析ツールで元に戻すことができます。

**フロントエンドに書いたキーは「インターネット上に公開した」のと同じです。**

### サーバーサイドのコードは「ユーザーに届かない」

サーバーサイドとは、サーバー上で動く部分です。データベースへの接続、外部 API の呼び出し、認証の検証などはサーバーサイドで行われます。

サーバーサイドのコードは、サーバーが処理した「結果（JSON など）」だけをユーザーに返します。コード自体はユーザーの手元に届きません。

> **フロントエンドとは？** ユーザーのブラウザ上で動く、画面に見える部分。HTML・CSS・JavaScript で構成され、ユーザーの端末上で実行されます。コードはブラウザから誰でも閲覧可能です。
>
> **サーバーサイドとは？** サーバー上で動く、ユーザーから見えない部分。データベースの読み書き、認証の管理、外部 API の呼び出しなどを担当します。コードはユーザーの端末に届かないため、キーを安全に保管できます。

## このカリキュラムで登場するキー一覧

| キー | 置ける場所 | 理由 |
|------|-----------|------|
| Supabase `publishable key` | フロント可（ただし RLS 必須） | RLS によってアクセス範囲が制限されている前提 |
| Supabase `service_role key` | サーバーのみ | RLS を完全にバイパスする。全データへのアクセス権を持つ |
| Vercel / その他 API キー | サーバーのみ | 外部サービスへの直接アクセス権を持つ |

「フロント可」の publishable key も、RLS が設定されていない状態では全データにアクセスできてしまいます。**「フロント可」は「RLS が有効である」ことが大前提**です。

## Next.js での安全な扱い方

### `.env.local` ファイルとは

Next.js では、キーなどの機密情報を `.env.local` というファイルに書いて管理します。このファイルは Git の管理対象から除外されており、GitHub にアップロードされません。

> **環境変数とは？** アプリの「設定値」を、コードの外側で管理する仕組みです。キーやパスワードをコードに直接書かず、環境変数として別ファイルに保管することで、安全に管理できます。

### `NEXT_PUBLIC_` プレフィックスのルール

Next.js には、変数名の先頭に `NEXT_PUBLIC_` を付けるかどうかで、フロントエンドに公開するかどうかを制御する仕組みがあります。

> **プレフィックスとは？** 名前の先頭に付けるひとかたまりの文字列です。たとえば `NEXT_PUBLIC_` という接頭辞（プレフィックス）を付けることで、その変数がフロントエンドに公開されることを Next.js に伝えます。

| 変数名の形式 | 公開範囲 | 用途 |
|-------------|---------|------|
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | フロントエンドで使える | publishable key など、公開してよいキー |
| `SUPABASE_SERVICE_ROLE_KEY` | サーバーサイドのみ | service_role key など、隠すべきキー |

### `.env.local` の書き方

```text
# Supabase
NEXT_PUBLIC_SUPABASE_URL=https://xxxxxxxxxxxx.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=eyJxxxxxxxxxxxxxxxxxx（publishable key）

# サーバーサイド専用（NEXT_PUBLIC_ を付けない）
SUPABASE_SERVICE_ROLE_KEY=eyJxxxxxxxxxxxxxxxxxx（service_role key）
```

### `.gitignore` と `.env.example` のセット運用

`.env.local` は Git の管理対象から除外されます（`.gitignore` に記載済み）。ただし、「どんな変数が必要か」を他の開発者に伝えるため、**値を空にした `.env.example` を Git に含める**のが一般的な運用です。

```text
# .env.example（GitHub に上げてよい）
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=
SUPABASE_SERVICE_ROLE_KEY=
```

このファイルを見れば「どんな変数が必要か」がわかりますが、値が空なので実際のキーは漏洩しません。

> **`.gitignore` とは？** Git が管理しないファイルやフォルダを指定するファイルです。`.env.local` をここに書いておくことで、うっかり `git add` しても GitHub にアップロードされません。

## 漏洩したら何が起きるか

### service_role key が漏洩した場合

service_role key は RLS を完全に無効化します。このキーが第三者に渡ると、データベース内のすべてのデータへの読み取り・書き換え・削除が可能になります。

「ユーザーの個人情報が全件流出する」「データが全件削除される」といった最悪の事態が起きます。

### publishable key が漏洩した場合（RLS なし）

RLS が設定されていない状態で publishable key が漏洩すると、service_role key が漏洩したのとほぼ同じ被害になります。publishable key の「安全性」は RLS の存在が前提です。

### 外部サービスの API キーが漏洩した場合

OpenAI や Stripe などの外部サービスの API キーが漏洩すると、以下のような被害が起きます。

- **不正利用による課金**: あなたのアカウントで無制限に API を使われ、多額の請求が来る
- **アカウント停止**: 不正利用の疑いでサービス側からアカウントを停止される
- **データへの不正アクセス**: そのサービスに保管しているデータを読み取られる

実際にこうした被害は頻繁に発生しています。GitHub に API キーを含むコードをうっかり公開した結果、数時間のうちに数十万円の請求が来た事例も報告されています。

## 実践チェックリスト

プロジェクトを始める前・GitHub にプッシュする前に、以下を確認してください。

- `.env.local` が `.gitignore` に含まれているか確認する
- GitHub のリポジトリに `service_role key` や `publishable key` が直接書かれたファイルがコミットされていないか確認する
- Supabase の管理画面でテーブルごとに RLS が有効になっているか確認する
- Vercel の「Environment Variables」設定画面で、機密キーが `NEXT_PUBLIC_` なしで設定されているか確認する

> **Vercel の環境変数設定とは？** Vercel のプロジェクト設定画面にある「Environment Variables」タブで、本番環境のキーを安全に設定できます。ここに登録した値は暗号化されて保管され、コードから環境変数として参照できます。GitHub のコードに直接書く必要はありません。

## まとめ

| ポイント | 内容 |
|---------|------|
| **キーの 2 分類** | 「フロント可（RLS 前提）」と「サーバーのみ」の 2 種類がある |
| **publishable key** | フロントに置けるが、RLS が有効であることが絶対条件 |
| **service_role key** | サーバーサイド専用。フロントに置くことは絶対禁止 |
| **`NEXT_PUBLIC_` ルール** | プレフィックスあり → フロント公開、なし → サーバー専用 |
| **`.env.local`** | キーの保管場所。Git 管理外のため GitHub に上がらない |
| **漏洩リスク** | service_role key 漏洩は DB 全体への無制限アクセスを意味する |
| **RLS の重要性** | publishable key の安全性は RLS の設定が前提。必ず有効にする |

> **覚えておきたい一文:** 「フロントエンドに書いたものは、インターネット上で公開したのと同じ」。権限の強いキーは必ずサーバーサイドに隔離し、`.env.local` で管理してください。
