## 1. ビルドとは何か

### 結論: ビルドは「開発用のコードを本番用に変換する工程」

> **ビルド（Build）とは？** 開発者が書いたコードをそのまま公開するのではなく、ブラウザが高速に処理できる形に変換・最適化する工程のことです。「組み立てる」「製造する」という意味の言葉から来ています。

**たとえ話:** ビルドは「原稿を書いてから印刷物を作る工程」のようなものです。ライターが書いた原稿（開発コード）は、読みやすさのために改行や余白がたっぷり入っています。しかし本として印刷するとき（ビルド）は、レイアウトを整え、文字を組んで、最終的な印刷データ（本番コード）に変換します。完成した印刷物は読者（ブラウザ）が読むために最適化されており、原稿の段階とは見た目が大きく変わっています。

### Next.js のビルドで何が起きるか

`npm run build` を実行すると、Next.js は裏側で以下の処理を順番に行います。

1. **型チェック（TypeScript のエラー確認）** — コードに矛盾がないかを厳格に検査する
2. **コードの圧縮（Minification）** — 変数名の短縮・空白の削除でファイルサイズを削減する
3. **ページの最適化** — どのページを事前に生成するか、どこをリアルタイムで処理するかを決定する
4. **静的ファイルの生成** — `.next/` フォルダにビルド済みのファイル群を出力する

```bash
# bash
npm run build
```

実行後、ターミナルに次のような出力が表示されます。

```text
# output
Route (app)                              Size     First Load JS
┌ ○ /                                    5.23 kB        87.3 kB
├ ○ /login                               3.12 kB        85.1 kB
└ ● /todos                               8.45 kB        90.5 kB

○  (Static)   prerendered as static content
●  (SSR)      server-side renders at runtime
```

これは「各ページのファイルサイズ」と「どの方式でページを生成するか」を示したものです。ビルドが成功すると、この一覧が表示されます。

### `npm run dev` との違い

| | `npm run dev`（開発モード） | `npm run build`（ビルド） |
|--|--------------------------|------------------------|
| 目的 | 手元で動作確認しながら開発する | 本番公開用のファイルを生成する |
| 速さ | 起動が速い（最適化しない） | 時間がかかる（最適化する） |
| 型チェック | 甘い（一部エラーを無視する） | 厳格（全エラーを検出する） |
| 出力先 | メモリ上（ファイルを作らない） | `.next/` フォルダ |

### 「開発中は動いていたのにビルドで失敗する」理由

開発モードで問題なく動いていたコードが、ビルド時にエラーになることがあります。これは型チェックの厳しさが違うためです。

開発モードは「動作確認を素早くする」ために、型のミスをある程度見逃します。しかし `npm run build` は「本番に出す前に問題をすべて発見する」ために、TypeScript の型エラーを 1 つ残らず指摘します。

> **TypeScript の型エラーとは？** 「文字列を入れる変数に数値を入れている」「存在しないかもしれないデータを存在する前提で使っている」といった、論理的な矛盾をコードが実行される前に発見する仕組みです。ビルド時にこれを厳格に検査することで、本番環境での予期しないクラッシュを防ぎます。

ビルドエラーが出たときは、Claude Code に「ビルドエラーを直して」と頼むのが最も手早い解決策です（詳しくは[セクション 5](#5-ビルドエラーの読み方)で説明します）。

## 2. デプロイとは何か

### 結論: デプロイは「アプリをサーバーに配置して公開すること」

> **デプロイ（Deploy）とは？** 「展開する」「配備する」という意味の言葉です。IT の世界では「ビルド済みのアプリをサーバーに乗せて、インターネット上で使えるようにすること」を指します。

**たとえ話:** デプロイは「手元の試作品を店頭に並べる工程」のようなものです。デザイナーがアトリエ（自分のパソコン）で作ったバッグは、自分だけが見られる状態です。お店に並べる（デプロイする）ことで、初めて世界中のお客さん（インターネットのユーザー）が手に取れるようになります。

### ローカル（自分のパソコン）と本番（Vercel のサーバー）の違い

| | ローカル（開発環境） | 本番（Vercel のサーバー） |
|--|-------------------|----------------------|
| アクセスできる人 | 自分だけ | インターネット上の誰でも |
| URL | `http://localhost:3000` | `https://あなたのアプリ.vercel.app` |
| 動いている場所 | 自分のパソコン | Vercel のデータセンター |
| 起動条件 | `npm run dev` を実行中のみ | 常時稼働（24時間） |

### Vercel が何をしてくれるのか

Vercel はデプロイに必要な作業を、ほぼすべて自動で行います。

| Vercel が担う作業 | 自力でやると必要なこと |
|----------------|---------------------|
| サーバーの用意・管理 | クラウドサービスの契約・設定 |
| HTTPS 化（セキュアな通信） | SSL 証明書の取得・更新 |
| CDN（世界中に高速配信） | グローバルなネットワーク設定 |
| 自動スケーリング（アクセス増加への対応） | 負荷分散の設計 |
| ビルドの実行 | CI サーバーの構築 |

> **CDN とは？** Content Delivery Network の略で、世界中にサーバーを分散配置して、ユーザーに最も近いサーバーからデータを届ける仕組みです。日本のユーザーには日本のサーバーから、アメリカのユーザーにはアメリカのサーバーから配信されるため、表示が速くなります。

> **HTTPS とは？** ブラウザとサーバー間の通信を暗号化するプロトコル（通信の約束事）です。URL が `https://` で始まっているサイトは暗号化されており、途中で通信内容を盗み見られることを防ぎます。Vercel はデプロイするだけで自動的に HTTPS を設定してくれます。

**たとえ話:** Vercel は「お店の全てを管理してくれる百貨店テナント」のようなものです。あなたは商品（アプリ）を持ち込むだけで、陳列棚（サーバー）・照明（CDN）・防犯システム（HTTPS）・来客対応（スケーリング）はすべて百貨店側が用意してくれます。

## 3. CI/CD とは何か

### 結論: GitHub に push するだけで自動でビルド・デプロイされる仕組み

> **CI/CD（シーアイシーディー）とは？** 「継続的インテグレーション（Continuous Integration）」と「継続的デリバリー（Continuous Delivery）」の略です。コードを変更するたびに、自動でテスト・ビルド・デプロイが走る仕組みを指します。

難しい言葉ですが、このカリキュラムでの体験としては**「GitHub に push したら、Vercel が自動でデプロイしてくれる」**の一言で表せます。

### CI と CD を分けて理解する

#### CI（継続的インテグレーション）— コードを自動でチェックする

> **CI（Continuous Integration）とは？** コードをリポジトリに統合するたびに、自動でビルドや型チェックを実行する仕組みです。「問題のあるコードが本番に混入するのを防ぐ門番」の役割を担います。

CI が行う主な作業：

- コードのビルド（エラーがないか確認する）
- 型チェック（TypeScript の矛盾を検出する）
- テスト（コードが期待どおりに動くか検証する）

#### CD（継続的デリバリー）— 自動で本番にデプロイする

> **CD（Continuous Delivery）とは？** CI のチェックを通過したコードを、自動で本番環境にデプロイする仕組みです。「承認されたコードを自動で店頭に並べる配送システム」のイメージです。

### GitHub → Vercel の自動デプロイの流れ

このカリキュラムで Vercel と GitHub を連携させると、以下の流れが自動で動きます。

1. あなたが Claude Code でコードを修正する
2. `git commit` で変更を記録する
3. `git push` で GitHub にコードを送る
4. Vercel が GitHub の変更を自動で検知する
5. Vercel がビルドを開始する（`npm run build` を実行する）
6. ビルドが成功する
7. 新しいバージョンが自動でデプロイされる
8. 公開 URL でアクセスすると最新版が表示される

**たとえ話:** CI/CD は「原稿を入稿したら自動で印刷・配送される仕組み」のようなものです。出版社に原稿（コード）を送る（push）と、校正（CI）が自動で走り、問題がなければ自動で印刷（ビルド）・全国配送（デプロイ）まで行われます。著者（あなた）は「原稿を送る」だけで、残りはすべて自動です。

また、コンベアベルトのたとえでもわかりやすく説明できます。工場（GitHub）にパーツ（コード）が届いたら、コンベアベルト（CI/CD パイプライン）が自動で検品（ビルド・チェック）し、梱包（デプロイ）して、出荷（公開）まで流れていきます。

### Preview Deploy（プレビューデプロイ）について

Vercel には、`main` ブランチ以外への push に対して「プレビュー URL」を自動発行する機能もあります。

| ブランチ | 生成される URL | 用途 |
|---------|-------------|------|
| `main` | 本番 URL（`https://xxx.vercel.app`） | 実際に公開するバージョン |
| それ以外（`feature/xxx` など） | プレビュー URL（`https://xxx-git-feature-xxx.vercel.app`） | レビューや確認用 |

> **プレビュー URL とは？** `main` に取り込む前の変更内容を、本番とは別の URL で確認できる機能です。「出版前のゲラ刷り」のように、実際に公開される前に見た目や動作を確認できます。

## 4. 環境変数（ローカル vs 本番）

### なぜローカルと本番で設定が変わるのか

アプリは「どの Supabase プロジェクトに接続するか」「API キーは何か」といった情報を、コードに直接書かずに**環境変数**として外部から受け取ります。

> **環境変数とは？** プログラムが参照できる「名前のついた設定値」です。コードの外側から渡す仕組みのため、同じコードでも「開発環境用の設定」「本番環境用の設定」を使い分けられます。

ローカル（自分のパソコン）では `.env.local` ファイルに書きます。しかし、このファイルは Git で管理されないため（`.gitignore` で除外されているため）、GitHub には存在しません。Vercel はコードを GitHub から受け取るため、`.env.local` の内容は届きません。

そのため、本番環境では Vercel のダッシュボードで環境変数を別途設定する必要があります。

### 比較表

| | ローカル（開発環境） | 本番（Vercel） |
|--|-------------------|--------------|
| 設定ファイル | `.env.local` | Vercel ダッシュボードの環境変数 |
| 公開範囲 | 自分のパソコンだけ | インターネット上 |
| 変更方法 | ファイルを編集して `source` か再起動 | Vercel の設定画面から変更 |
| Git 管理 | されない（`.gitignore` で除外） | 関係ない（ダッシュボードで管理） |

### `.env.local` はローカルだけで使う

`.env.local` は Git の管理対象外です。GitHub に push しても、このファイルは含まれません。これは意図的な設計です。API キーなどの機密情報が GitHub に公開されることを防ぐためです。

```text
# output
.gitignore（抜粋）

# local env files
.env*.local      ← .env.local はここで除外されている
```

**たとえ話:** `.env.local` は「自宅の冷蔵庫の中身」のようなものです。自宅（ローカル）にある食材（API キー）は、お店（本番 Vercel）には自動では運ばれません。お店用の食材は、お店に直接仕入れる（Vercel のダッシュボードで設定する）必要があります。

### `NEXT_PUBLIC_` のついた変数に注意する

Next.js には 2 種類の環境変数があります。

| 変数名の形式 | ブラウザからのアクセス | 用途 |
|------------|------------------|------|
| `NEXT_PUBLIC_変数名` | できる（公開される） | Supabase の URL・ANON KEY など |
| `変数名`（プレフィックスなし） | できない（サーバーのみ） | 秘密鍵・決済キーなど |

`NEXT_PUBLIC_` がついた変数はブラウザの開発者ツールから確認できます。これは設計上の仕様であり、Supabase の ANON KEY のようにブラウザに公開することが前提の値に使います。

逆に、`service_role key`（Supabase の管理者キー）のような「絶対に公開してはいけない値」には絶対に `NEXT_PUBLIC_` をつけないでください。

> **セキュリティの原則:** ブラウザに公開される変数は「公開されても安全な値のみ」に限定する。`NEXT_PUBLIC_` をつけてしまった秘密情報は、インターネット上に漏れたのと同じです。

## 5. ビルドエラーの読み方

### ビルドエラーが出たときにまず確認すること

`npm run build` を実行してエラーが出たとき、ターミナルに表示される内容を確認します。エラーは必ずファイル名と行番号とともに表示されます。

```text
# output
./src/app/todos/page.tsx
Type error: Type 'string | undefined' is not assignable to type 'string'.

  17 |   const userId = session?.user?.id
  18 |
> 19 |   fetchTodos(userId)
     |              ^^^^^^
  20 |
```

この例では「`17 行目` で取得した `userId` が `undefined` かもしれないのに、`undefined` を受け付けない関数に渡している」というエラーです。

### よくあるエラーの種類

| エラーの種類 | 典型的なメッセージ | 原因 |
|-----------|-----------------|------|
| **型エラー** | `Type 'X' is not assignable to type 'Y'` | 変数の型が合っていない |
| **import エラー** | `Module not found: Can't resolve '...'` | 存在しないファイルを読み込もうとしている |
| **環境変数の未設定** | `Cannot read properties of undefined` | 環境変数が設定されていないため `undefined` になっている |
| **存在しない可能性** | `Object is possibly 'undefined'` | `null` や `undefined` の可能性をケアしていない |

### Claude Code に頼む方法

ビルドエラーが出たら、エラーメッセージをそのままコピーして Claude Code に貼り付け、以下のように依頼します。

```plaintext
# claude
npm run build したらエラーが出ました。直してください。

[エラーメッセージをここに貼り付ける]
```

Claude Code はエラーメッセージから原因を特定し、修正を行います。自分でエラーの内容を完全に理解する必要はありません。「何かがおかしい」とわかったら、すぐ Claude Code に投げてください。

## 6. デプロイの流れ（このカリキュラムの場合）

このカリキュラムで行う Vercel デプロイの全体フローを整理します。

```text
# output
コードを書く（Claude Code）
  ↓
git commit & push（GitHub にコードを送る）
  ↓
Vercel が自動検知してビルド開始
  ↓
ビルド成功 → 自動デプロイ完了
  ↓
公開 URL でアクセス可能に
```

各ステップで何が起きているかをもう少し詳しく見ていきます。

**Step 1: コードを書く（Claude Code）**

Claude Code がコードを作成・修正します。変更はまだ自分のパソコンにのみ存在します。

**Step 2: git commit & push（GitHub）**

`git commit` で変更を記録し、`git push` で GitHub のリポジトリにコードを送ります。この瞬間に、コードがクラウドに存在するようになります。

**Step 3: Vercel が自動検知してビルド開始**

GitHub への push を Vercel が検知します（Webhook という仕組みで通知が届きます）。Vercel 側で `npm run build` が自動実行されます。

> **Webhook（ウェブフック）とは？** 「何かが起きたら自動で通知する」仕組みです。GitHub が「push があった」と Vercel に通知するために使われています。あなたが特別な操作をする必要はありません。

**Step 4: ビルド成功 → 自動デプロイ完了**

ビルドが成功すると、生成されたファイルが Vercel のサーバーに配置されます。数秒〜数分で完了します。

**Step 5: 公開 URL でアクセス可能に**

デプロイが完了すると、公開 URL（`https://あなたのアプリ.vercel.app`）で最新版が表示されます。Vercel のダッシュボードでデプロイ状況をリアルタイムで確認できます。

## 7. まとめ — よく使う言葉の整理

このカリキュラムで登場するデプロイ関連の言葉を、平易にまとめます。

| 用語 | 一言での説明 | たとえ |
|------|-----------|------|
| **ビルド** | 開発用コードを本番用に変換する工程 | 原稿を印刷物に仕上げる |
| **デプロイ** | アプリをサーバーに配置して公開すること | 試作品を店頭に並べる |
| **CI/CD** | push するだけで自動でビルド・デプロイされる仕組み | 原稿を入稿したら自動で印刷・配送 |
| **本番環境** | 実際にインターネット上で公開されている環境 | お客さんが入れる本物の店舗 |
| **開発環境** | 自分のパソコン上で動かしている環境 | 手元のアトリエ |
| **環境変数** | コードの外側から渡す設定値（API キーなど） | 店ごとに異なる「秘密のレシピ」 |

> **覚えておきたい一文:** 「ビルドで本番用に変換し、デプロイでサーバーに乗せる。GitHub に push するだけで CI/CD がこの 2 つを自動でやってくれる」——この流れを頭に入れておけば、Chapter 6 のハンズオンがぐっとわかりやすくなります。
