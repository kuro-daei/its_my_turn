## 1. Supabase とは — 全体像をつかむ

Supabase（スーパーベース）は「データベース専用サービス」ではありません。

**Supabase とは、アプリ開発に必要なバックエンド機能をまるごと提供するクラウドサービスです。**

> **バックエンドとは？** アプリには「画面に見える部分（フロントエンド）」と「データを管理・処理する部分（バックエンド）」の 2 つがあります。バックエンドは、データベースへのデータの保存、ユーザーの認証（ログイン）、ファイルの管理など、ユーザーからは見えないところで動く仕組みの総称です。

Supabase を一言で表すなら「アプリの"裏方"を一式そろえてくれるサービス」です。データベース・認証・ストレージといった機能が、最初からセットになっています。

**たとえ話:** Supabase は「新築マンションの管理会社」のようなものです。入居者（あなたのアプリ）が引っ越してくるだけで、電気・水道・宅配ボックス・エントランスのオートロックがすでに整っています。自分で電気工事や水道工事をする必要はありません。データベース（電気）も認証（オートロック）も、プロジェクトを作った瞬間からすぐ使えます。

Supabase が提供する主な機能は以下の 4 つです。

| 機能 | できること |
|------|----------|
| **データベース** | データを保存・管理・検索する |
| **認証（Auth）** | ユーザーのログイン・ログアウトを管理する |
| **ストレージ** | 画像・動画などのファイルを保存・配信する |
| **Realtime** | データの変更をリアルタイムにアプリへ届ける |

この 4 つのうち、このカリキュラムで中心的に使うのは**データベース**と**認証**の 2 つです。そして、この 2 つは深く連携しています。その連携の話が、この資料の核心です。

## 2. 機能 1: データベース

### データベースとは

> **データベースとは？** 大量のデータを整理して保存・検索できる仕組みです。Excel のスプレッドシートをイメージしてもらうと近いですが、データベースは「複数の表が連携できる」「大量データを高速に検索できる」「複数人が同時にアクセスしても壊れない」といった点で格段に強力です。

Supabase が使っているデータベースは **PostgreSQL（ポストグレスキューエル）**です。世界中のサービスで使われている、実績・信頼性ともに最高クラスのデータベースです。

**たとえ話:** PostgreSQL は「高性能な電子カルテシステム」のようなものです。医療現場で何百万人分ものカルテを安全に管理できるように設計されており、データが壊れたり消えたりすることなく、素早く正確に必要な情報を取り出せます。

### テーブルという単位

データベースは「テーブル（表）」という単位でデータを管理します。

**たとえ話:** データベースが「図書館」なら、テーブルは「ジャンル別の棚」です。「TODO の棚（todos テーブル）」「ユーザーの棚（users テーブル）」というように、種類ごとに分けて管理します。

このカリキュラムの TODO アプリでは `todos` テーブルを作ります。テーブルは「列（カラム）」と「行（レコード）」で構成されます。

```text
# output
todos テーブル（イメージ）

| id | user_id | title         | is_done | created_at         |
|----|---------|---------------|---------|--------------------|
|  1 | abc123  | 買い物に行く   | false   | 2024-01-10 09:00   |
|  2 | abc123  | メールを返す   | true    | 2024-01-10 10:30   |
|  3 | xyz789  | 資料を作る     | false   | 2024-01-10 11:00   |
```

各列（カラム）の役割は次のとおりです。

| カラム | 内容 |
|-------|------|
| `id` | この行を識別する番号（自動で付与） |
| `user_id` | どのユーザーの TODO か（認証と連携） |
| `title` | TODO の内容 |
| `is_done` | 完了したかどうか |
| `created_at` | 作成日時 |

### ダッシュボードで確認・編集できる

Supabase のダッシュボードには「Table Editor」という画面があります。コードを書かなくても、スプレッドシートのようにテーブルの中身を見たり、直接データを入力・編集したりできます。

> **体験:** Chapter 3 の Step 3 でテーブルを作った後、ダッシュボードの Table Editor でデータが入っている様子を確認できます。

### API が自動生成される

Supabase はテーブルを作ると、そのテーブルに対応する API を自動で生成します。

> **API（エーピーアイ）とは？** アプリとデータベースが「話すための窓口」です。アプリが「TODO を全部取ってきて」と API に頼むと、データベースがデータを返してくれます。手紙の宛先のようなもので、宛先さえ正しければ、アプリ側の言語に関係なく通信できます。

この自動生成のおかげで、Next.js アプリから「接続情報（URL と API キー）を設定するだけ」でデータを読み書きできるようになります。

## 3. 機能 2: 認証（Auth）

### 認証とは

> **認証（Auth）とは？** 「あなたは誰か」を確認する仕組みです。ユーザーが「私は田中です」とログインしてきたとき、本当に田中さん本人かどうかを確認し、その人専用のデータへのアクセスを許可します。

Supabase の Auth が提供するログイン方式は複数あります。

| ログイン方式 | 説明 |
|-----------|------|
| **メール ＋ パスワード** | 一般的なIDとパスワードでの認証 |
| **マジックリンク** | メールアドレスだけ入力すると、ログイン専用 URL がメールで届く（パスワード不要） |
| **Google ログイン** | Google アカウントでワンクリックでログインする |
| **GitHub ログイン** | GitHub アカウントでワンクリックでログインする |

このカリキュラムではメール/パスワード認証を使います。

### 認証情報はデータベースに保存される

ここが重要な点です。

**Supabase Auth のユーザーデータは、同じ Supabase プロジェクトのデータベースに保存されています。**

具体的には、データベースの中に `auth` という領域（スキーマ）があり、そこにユーザー一覧が保管されています。

> **スキーマとは？** データベースの中を「区画」で分ける仕組みです。`auth` スキーマはユーザー認証専用の区画で、Supabase が自動的に管理します。あなたが作る `todos` テーブルは `public` スキーマに入ります。

**たとえ話:** マンション（データベース）の中に「居住者名簿の部屋（auth スキーマ）」と「各入居者の倉庫（public スキーマ）」が共存しているイメージです。居住者名簿は管理会社が管理し、倉庫はあなたが自由に使えます。でも、どちらも同じマンションの中にあるため、「この倉庫は誰のものか」を名簿と照合することが素早くできます。

このように、**Auth とデータベースは最初からひとつのプロジェクトの中にあります。** これが「2 つがセット」である最大の理由です。

### JWT — 認証の証明書

ユーザーがログインすると、Supabase は **JWT（ジェイダブリューティー）** と呼ばれる「認証済み証明書」を発行します。

> **JWT（JSON Web Token）とは？** ログイン済みのユーザーに発行される「デジタルの入場証」です。「このユーザーは認証済みで、ID は abc123 だ」という情報が安全に暗号化されています。アプリはこの入場証をデータベースへのリクエストに添付することで、「誰がリクエストしているか」を伝えられます。

**たとえ話:** JWT は映画館の「チケット半券」のようなものです。チケットを購入したことの証明であり、「この席は私のもの」を示す情報が入っています。スタッフ（データベース）はこの半券を見て、「正規の入場者だ」と判断してデータへのアクセスを許可します。

## 4. データベースと認証はつながっている — RLS

### なぜ 2 つがセットである必要があるのか

データベースと認証が別々のサービスだったとしたら、どうなるでしょうか。

TODO アプリで考えてみます。田中さんが「TODO 一覧を取得する」という操作をするとき、データベースには田中さんのデータだけでなく、鈴木さんのデータも山田さんのデータも入っています。認証サービスが「田中さんがログインしている」と知っていても、データベースがそれを知らなければ、田中さんに全員分の TODO を返してしまいます。

これを防ぐために、**「ログインしているのが誰か」をデータベースが把握して、自動でアクセスを制限する仕組み**が必要です。それが **RLS（Row Level Security）** です。

### RLS とは

> **RLS（Row Level Security）とは？** 「ログインしているユーザー自身のデータだけアクセスできる」というルールを、データベース側に設定できる仕組みです。アプリのコード側ではなく、データベース自体にルールが組み込まれているため、コードにうっかりミスがあっても他人のデータが漏れることを防げます。

RLS の「Row（行）」は、テーブルの「1 行分のデータ」を指します。つまり RLS は「行レベルで誰がアクセスできるかを制御する」仕組みです。

**たとえ話:** RLS は「社員証で入室管理された会社のロッカー」のようなものです。ロッカールーム（データベース）には全社員分のロッカーがありますが、自分の社員証（JWT）を使わないと自分のロッカーしか開けられません。受付（アプリのコード）がいなくても、ロッカー側（データベース）が自動で「この社員証で開けられるのはこのロッカーだけ」とはじきます。

### RLS がどう動くか

Chapter 3 で設定した RLS ポリシーの意味を解説します。

```text
# output
ルール: todos テーブルの行は、その行の user_id が
        現在ログインしているユーザーの ID と一致する場合のみアクセス可能
```

この設定が動作する仕組みは次のとおりです。

1. 田中さんがアプリにログインする
2. Supabase Auth が JWT（ID: `abc123`）を発行する
3. アプリが「TODO を取得して」とデータベースに要求する（JWT も一緒に送る）
4. データベースが JWT から「ログインしているのは `abc123`」を確認する
5. `todos` テーブルから `user_id = abc123` の行だけを返す
6. 田中さんの画面には田中さんの TODO だけが表示される

```text
# output
todos テーブル

| id | user_id | title       |    ← RLS フィルタ後
|----|---------|-------------|
|  1 | abc123  | 買い物に行く |    ← 田中さんには見える
|  2 | abc123  | メールを返す |    ← 田中さんには見える
|  3 | xyz789  | 資料を作る   |    ← 田中さんには見えない（鈴木さんのデータ）
```

### 2 つがセットである理由のまとめ

- **Auth がなければ RLS は動かない** — 「誰がログインしているか」がわからなければ、アクセスを制限できません
- **データベースがなければ Auth は完結しない** — ユーザーデータを保存する場所が必要です
- **同じプロジェクトの中にあるから連携できる** — Auth が発行した JWT を、データベースが即座に検証できます

Supabase がデータベースと認証を一体で提供しているのは、「この 2 つが連携してはじめてセキュアなアプリができる」という設計思想があるためです。

## 5. 機能 3 以降: Storage・Realtime・Edge Functions

このカリキュラムでは使いませんが、Supabase が提供する他の機能も紹介しておきます。

### Storage（ストレージ）

> **Storage とは？** 画像・動画・PDF などのファイルをアップロードして保存・配信できる機能です。データベースが「テキストや数値のデータ」を管理するのに対し、Storage は「ファイルそのもの」を管理します。

**たとえ話:** データベースが「住所録（名前・電話番号などの情報）」なら、Storage は「アルバム（写真そのもの）」です。「プロフィール画像を保存して表示する」「PDF の資料をアップロードしてダウンロードできるようにする」といった用途に使います。

RLS と同じように、Storage にもアクセス制御のポリシーを設定できます。「自分がアップロードしたファイルしか削除できない」といったルールを設けられます。

### Realtime（リアルタイム）

> **Realtime とは？** データベースの変更を、ブラウザに即座に届ける機能です。「ページをリロードしなくても、誰かがデータを追加した瞬間に画面が更新される」という体験を実現します。

**たとえ話:** 通常のデータベース問い合わせが「手紙のやり取り」なら、Realtime は「電話」です。チャットアプリの「相手がメッセージを送った瞬間に画面に届く」体験は、Realtime なしには実現できません。

### Edge Functions（エッジファンクション）

> **Edge Functions とは？** サーバーサイドで動く軽量なプログラムを、Supabase 上でホスティングできる機能です。「データを保存する前に加工したい」「外部サービスと連携したい」といった処理を、アプリのコードを変えずに実装できます。

## 6. ダッシュボードのよく使う画面

Supabase のダッシュボードで操作する主な画面を整理します。

| 画面 | 用途 |
|------|------|
| **Table Editor** | テーブルの中身をスプレッドシートのように閲覧・編集する |
| **SQL Editor** | SQL（データベースへの命令言語）を直接実行してデータを操作する |
| **Authentication → Users** | 登録済みユーザーの一覧を確認する |
| **Authentication → Providers** | Google・GitHub などのソーシャルログインの有効化設定を行う |
| **Authentication → Policies** | RLS ポリシーの確認・追加・編集を行う |
| **Project Settings → API Keys** | アプリと接続するための API キーを確認する |

> **体験:** Chapter 3 の Step 3 でテーブルを作った後、Table Editor を開いてみてください。「todos テーブルが作成されている」「RLS が有効になっている」ことをダッシュボードで目視確認できます。

## 7. よく出てくる用語

### プロジェクト

> **プロジェクトとは？** Supabase 上の「1 つのアプリ用の環境」です。プロジェクトを作ると、データベース・認証・ストレージ・Realtime がすべてセットで用意されます。「アプリの箱」のようなもので、複数のアプリを作るなら複数のプロジェクトを用意します。

このカリキュラムでは `todos` という名前のプロジェクトを 1 つ作ります。

### API キー（anon key / service_role key）

アプリが Supabase に接続するために必要な「パスワード」のようなものです。2 種類あります。

| キー | 用途 | 注意点 |
|-----|------|-------|
| **anon key** | ブラウザ（フロントエンド）からの読み取りに使う | ブラウザに公開される（RLS で保護する） |
| **service_role key** | サーバーサイドでのデータ操作に使う | **絶対に公開してはいけない** |

> **anon key は「公開鍵」ではない:** anon key はブラウザから見えますが、それ自体でデータが盗まれるわけではありません。RLS（Row Level Security）が設定されていれば、anon key を使ってもアクセスできるのは「その認証ユーザーが許可されたデータのみ」です。ただし RLS が未設定の場合は全データにアクセスできてしまうため、テーブル作成時に必ず RLS を有効にしてください。

> **service_role key は絶対に公開してはいけない:** このキーは RLS を無視して全データにアクセスできます。`.env.local` に保存して、絶対にブラウザには公開しないでください。Next.js の環境変数に `NEXT_PUBLIC_` をつけると自動でブラウザに公開されてしまうため、service_role key の変数名には絶対に `NEXT_PUBLIC_` をつけないでください。

### 接続 URL

アプリが「どの Supabase プロジェクトに接続するか」を識別するためのアドレスです。

```text
# output
https://xxxxxxxxxx.supabase.co
         ↑
         プロジェクト固有の ID
```

`.env.local` の `NEXT_PUBLIC_SUPABASE_URL` に設定する値がこれです。

### `.env.local`

アプリの「秘密のメモ帳」として機能するファイルです。API キーや接続 URL などの機密情報を保存します。

```text
# output
# .env.local の中身（イメージ）
NEXT_PUBLIC_SUPABASE_URL=https://xxxxxxxxxx.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

このファイルは Git で管理されません（`.gitignore` に含まれている）。GitHub などに公開されることなく、自分のパソコンにのみ存在します。

## 8. まとめ

この補足資料で解説した内容を整理します。

```text
# output
Supabase の全体像

┌─────────────────────────────────────────────┐
│               Supabase プロジェクト           │
│                                             │
│  ┌──────────────┐   ┌────────────────────┐  │
│  │  データベース  │   │   認証（Auth）      │  │
│  │              │   │                    │  │
│  │  todos テーブル│◄──│  ユーザー情報(auth) │  │
│  │  （あなたのデータ）│   │  ＋ JWT 発行       │  │
│  │              │   │                    │  │
│  │  RLS で      │   │  メール・Google 等  │  │
│  │  アクセス制御 │   │  複数のログイン方式 │  │
│  └──────────────┘   └────────────────────┘  │
│         ↑ 連携（認証情報でアクセス制御）       │
│                                             │
│  Storage / Realtime / Edge Functions（補助） │
└─────────────────────────────────────────────┘
```

重要なポイントを 3 つにまとめます。

1. **Supabase はデータベース専用サービスではない** — データベース・認証・ストレージ等を一体で提供するバックエンドプラットフォームです。プロジェクトを作るだけで全機能がすぐ使えます

2. **データベースと認証は最初からつながっている** — Auth のユーザーデータは同じプロジェクトのデータベースに保存されています。このセット設計が RLS を可能にします

3. **RLS がセキュリティの要（かなめ）** — 「自分の TODO だけ見える・操作できる」という動作は、Auth（誰がログインしているか）とデータベース（どのデータを返すか）が連携することで実現しています

> **覚えておきたい一文:** Supabase は「データベースと認証の両方をセットで提供するサービス」です。2 つが同じプロジェクトにあることで、RLS という仕組みを通じて「自分のデータだけアクセスできる」という安全なアプリが自然に作れます。コードを書かなくてもこの仕組みが動くのが、Supabase の強みです。
