# Chapter 7: テスト・CI・Vercel デプロイ

**所要時間**: 約 1.5 時間
**ゴール**: テスト・CI・デプロイを一気に体験し、公開 URL で TODO アプリが動いている状態にする
**学ぶ Claude Code 機能**: テスト生成、GitHub Actions CI、Vercel MCP、CI/CD 連携、本番設定

---

## このチャプターで学ぶこと

- テストとは何かを理解し、Claude Code にテストコードを自動生成してもらう
- GitHub Actions を使って CI（継続的インテグレーション）パイプラインを構築する
- Vercel MCP を使って Claude Code から自然言語でデプロイを操作する
- GitHub にリポジトリを作成してコードを push する
- Vercel MCP で環境変数を設定してデプロイを実行する
- 公開 URL でアプリの動作を確認する
- Supabase の本番用 URL を設定する
- GitHub への push が「テスト → ビルド → デプロイ」まで自動でつながる仕組みを体験する

全部終わったら、インターネット上に公開された自分の TODO アプリが完成します。

---

## はじめに：「テストして、デプロイして」の一言で公開できる

**このチャプターの結論から言います。** Claude Code に「テストを書いて」と一言伝えればテストコードが自動生成され、「Vercel にデプロイして」と伝えるだけでアプリがインターネットに公開されます。

Chapter 6 まででローカル環境（自分のパソコン）で動く TODO アプリが完成しました。しかし今の状態では、あなたのパソコン上でしか動いていません。「インターネット上で誰でも見られる URL」にするには、**デプロイ**という作業が必要です。

> **デプロイ（deploy）とは？** 「展開する」「配備する」という意味の言葉です。IT の世界では「アプリをサーバーに乗せて、インターネット上で使えるようにすること」を指します。自分の部屋で作った料理をレストランで提供し始めるイメージです。

このチャプターでは、デプロイの前にもう一つ重要なステップを体験します。それが「テスト」と「CI（継続的インテグレーション）」です。

- **テスト**: アプリが正しく動くかを自動で確認する仕組み
- **CI**: コードを push するたびに自動でテスト・ビルドが走る仕組み
- **デプロイ**: テストとビルドが通ったコードをサーバーに公開する

この「テスト → CI → デプロイ」の流れを、Claude Code と Vercel MCP を使って一気に体験します。

> **ホスティングサービスとは？** アプリを動かし続けてくれるサーバーを貸してくれるサービスです。自分のパソコンを 24 時間稼働させなくても、Vercel のサーバーが代わりにアプリを動かし続けてくれます。

間違えても大丈夫です。途中でわからなくなったら、すぐメンターに声をかけてください。

## Step 1: GitHub リポジトリの準備（15分）

このステップでは、GitHub にリポジトリを作成してコードを push します。Vercel は GitHub のリポジトリと連携することで、push するたびに自動デプロイを行います。

> **リポジトリとは？** コードとその変更履歴をまとめて保管する「コードの倉庫」です。GitHub はこの倉庫をインターネット上で管理してくれるサービスです。

### 1-1. GitHub にリポジトリを作成する

**GitHub リポジトリがまだない場合:**

1. ブラウザで `https://github.com/new` を開く
2. 「Repository name」に `its_my_turn`（またはプロジェクト名）を入力する
3. Public または Private を選択する（どちらでも動作します）
4. 「Create repository」をクリックする

[screenshot: GitHub の新規リポジトリ作成画面]

5. 表示された URL（`https://github.com/あなたのユーザー名/its_my_turn.git`）をメモしておく

> **GitHub アカウントがない場合は？** `https://github.com` でアカウントを作成してください。GitHub は世界中の開発者がコードを公開・共有するためのサービスです。

### 1-2. GitHub にコードを push する

Claude Code に以下のように依頼します。

> GitHub にコードを push する準備をして。リモートリポジトリの URL は `https://github.com/あなたのユーザー名/its_my_turn.git`

Claude Code が必要な Git コマンドを順番に実行してくれます。または、以下のコマンドを直接実行することもできます。

```bash
# リモートリポジトリを登録する
git remote add origin https://github.com/あなたのユーザー名/its_my_turn.git

# 現在のブランチを確認する
git branch --show-current

# main ブランチに push する（初回のみ -u オプションが必要）
git push -u origin main
```

> **push とは？** ローカル（自分のパソコン）にあるコードを、GitHub のサーバー（リモート）に送信することです。手元で書いた原稿を出版社に送るイメージです。

[screenshot: ターミナルで git push が成功した様子]

> **注意:** `feature/deploy` ブランチで作業している場合は、先に main にマージしてから push するか、Vercel にはブランチを直接連携することもできます。メンターに確認してください。

### Step 1 の確認ポイント

- [ ] GitHub にリポジトリが作成されている
- [ ] `git remote -v` でリモートリポジトリの URL が表示される
- [ ] `git push` が成功している
- [ ] GitHub のリポジトリページでコードが表示されている

## Step 2: テストを書く & GitHub Actions で CI を設定（25分）

このステップでは、Claude Code にテストを書いてもらい、GitHub Actions で CI（継続的インテグレーション）を設定します。「テストって何？」という方も、まずは概念から理解していきましょう。

### 2-1. テストとは何か

**テストとは、アプリが正しく動くかを自動で確認する仕組みです。**

たとえ話で考えてみましょう。レストランのオープン前、シェフは「料理が正しく出来上がっているか」を必ず確認します。これを毎日手動でやるのは大変です。もし「確認ロボット」がいて、自動で「スープの温度は適切か」「味は正しいか」をチェックしてくれたら、シェフは料理の改善に集中できます。

プログラムの世界でも同じです。

- 機能を追加するたびに「ログインはまだ動くか」「TODO は追加できるか」を手動で確認するのは大変
- テスト（確認プログラム）を書いておけば、コマンド一つで全機能の確認が自動で終わる
- 「どこかが壊れていないか」を常に安心して確認できる

> **なぜテストが必要なの？** コードを変更すると、意図せず別の部分が壊れることがあります（これを「デグレ」と言います）。テストがあれば「変更したら別の機能が壊れた」という問題を即座に検知できます。

### 2-2. Claude Code にテストを書いてもらう

Claude Code に以下のように依頼します。

> TODO アプリの基本的なテストを書いて。Vitest を使って、コンポーネントの表示と CRUD 操作が正しく動くことを確認するテストを作って

> **Vitest とは？** React アプリのテストを書くための定番ツールです。「このボタンをクリックしたらこの動作が起きるはず」というシナリオをコードで表現できます。

Claude Code は以下の作業を順番に行います。

1. Vitest と testing-library（テスト用のツール群）をインストールする
2. テストの設定ファイルを作成する
3. テストコードを生成する
   - `AddTodoForm` コンポーネントが正しく表示されるかのテスト
   - `TodoItem` コンポーネントの表示・完了・削除のテスト
   - TODO の追加・一覧表示が正しく動くかのテスト

テストが生成されたら、ローカルで実行して確認します。

```bash
npm test
```

[screenshot: テストがすべてパスした様子（緑色のチェックマーク）]

テストが通れば「アプリの基本機能が正しく動作している」ことが自動確認できた状態です。

### Step 2（テスト）の確認ポイント

- [ ] Vitest がインストールされている（`package.json` に記載がある）
- [ ] テストファイルが生成されている（`*.test.ts` または `*.spec.ts` のファイル）
- [ ] `npm test` が実行できる
- [ ] テストがすべてパス（成功）している

### 2-3. CI（継続的インテグレーション）とは

テストが書けたら、次は「コードを push するたびに自動でテストが走る仕組み」を作ります。これが **CI（Continuous Integration、継続的インテグレーション）** です。

たとえ話で考えてみましょう。レストランに新メニューを追加するたびに、保健所が自動で「衛生検査」をしてくれるイメージです。

- 新メニュー（新機能）を追加する = GitHub に push する
- 保健所の検査 = CI がテスト・ビルドを自動実行する
- 検査に通れば = テストが全部パスすれば、安心してデプロイできる
- 検査に落ちれば = テストが失敗すれば、問題を修正してから再挑戦する

> **GitHub Actions とは？** GitHub が提供する CI/CD サービスです。無料で使えて、GitHub のリポジトリに `.github/workflows/` というフォルダに設定ファイルを置くだけで動きます。「push したら自動でこういう処理をして」という手順を YAML ファイルで記述します。

### 2-4. GitHub Actions のワークフローを作る

Claude Code に以下のように依頼します。

> GitHub Actions のワークフローファイルを作って。push 時に lint、テスト、ビルドが順番に実行されるようにして

Claude Code は以下の作業を行います。

1. `.github/workflows/ci.yml` を生成する
2. push または Pull Request 時に自動で以下が順番に実行されるよう設定する:
   - コードのチェックアウト（GitHub からコードを取得）
   - Node.js のセットアップ
   - 依存パッケージのインストール（`npm ci`）
   - Lint（コードの品質チェック）
   - テストの実行
   - ビルド（本番用ファイルの生成）

> **Lint とは？** コードの書き方が正しいかをチェックするツールです。「この変数は使われていない」「セミコロンが抜けている」などの問題を自動で検出します。

生成されるワークフローファイルのイメージは以下のとおりです（実際は Claude Code が生成します）。

```yaml
# .github/workflows/ci.yml のイメージ（実際は Claude Code が生成します）
name: CI
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npm run lint
      - run: npm test
      - run: npm run build
```

ワークフローファイルを GitHub に push した後、GitHub のリポジトリ画面で「Actions」タブを開きます。自動でテスト・ビルドが実行されていることを確認しましょう。

[screenshot: GitHub Actions の実行結果（すべてのステップが緑色で成功している様子）]

> **YAML とは？** 設定ファイルを書くための書き方（形式）のひとつです。インデント（字下げ）で構造を表現します。Claude Code に「ワークフローファイルを作って」と依頼すれば、自分でこの形式を覚える必要はありません。

### Step 2（CI）の確認ポイント

- [ ] `.github/workflows/ci.yml` が作成されている
- [ ] GitHub に push できている
- [ ] GitHub の Actions タブでワークフローが実行されている
- [ ] lint → test → build がすべて成功（緑色）になっている

## Step 3: Vercel のセットアップ & デプロイ（20分）

このステップでは、Vercel のアカウントを作成し、Vercel MCP をインストールして、Claude Code からデプロイを実行します。

### 3-1. Vercel アカウントの作成

まだ Vercel アカウントを持っていない場合は作成します。

1. ブラウザで `https://vercel.com` を開く
2. 「Sign Up」をクリックする
3. 「Continue with GitHub」を選択する（GitHub アカウントで連携するのが最も簡単です）
4. GitHub の認証を許可する

[screenshot: Vercel のサインアップ画面]

> **無料プラン（Hobby）で十分です。** 個人プロジェクトのデプロイは無料プランで問題なく動作します。クレジットカードの登録は不要です。

### 3-2. Vercel MCP のインストール

次に、Claude Code から Vercel を操作するための **Vercel MCP** をインストールします。

> **MCP（Model Context Protocol）とは？** AI と外部サービスをつなぐ「標準規格」です。USB-C のケーブルを思い浮かべてください。USB-C は「どのデバイスにも使えるケーブルの形」という標準規格です。MCP は「AI がどのサービスとも話せるためのつなぎ方の標準規格」です。この規格に対応したサービスは、Claude Code から自然言語で操作できるようになります。

ターミナルで以下のコマンドを実行します。

```bash
claude mcp add --transport http vercel https://mcp.vercel.com
```

インストールできたか確認します。

```bash
claude mcp list
```

`vercel` が表示されていれば設定完了です。

**初回認証について:**

Claude Code で Vercel の操作を最初に行うとき、ブラウザが自動で開いて認証画面が表示されます。「Allow（許可）」をクリックして認証を完了させてください。認証が完了すると、以後は自動的に認証が維持されます。

> **OAuth（オーオース）認証とは？** 「○○のアカウントでログイン」という仕組みです。新しいサービスのためにパスワードを新たに作る代わりに、すでに持っているアカウント（この場合は Vercel のアカウント）で安全に認証します。Claude Code が必要なトークン（通行証）を自動で管理するため、一度認証すれば以後は意識する必要がありません。

### 3-3. Vercel MCP でできること

Vercel MCP は以下のカテゴリのツールを提供しています。自然言語で依頼すると、Claude Code が適切なツールを自動で選んで使います。

**デプロイ操作**

| ツール | できること | 指示の例 |
|--------|-----------|---------|
| `deploy_to_vercel` | デプロイを実行する | 「Vercel にデプロイして」 |
| `list_deployments` | デプロイの一覧・状況を確認する | 「最新のデプロイ状況を教えて」 |
| `get_deployment` | 特定のデプロイの詳細を確認する | 「今動いているデプロイの情報を教えて」 |
| `get_deployment_build_logs` | ビルドログを取得する | 「デプロイが失敗した原因を調べて」 |
| `get_runtime_logs` | 本番のランタイムログを取得する | 「本番のエラーログを確認して」 |
| `use_vercel_cli` | Vercel CLI コマンドを実行する | 「Vercel CLI で環境変数を設定して」 |

**プロジェクト管理**

| ツール | できること | 指示の例 |
|--------|-----------|---------|
| `list_projects` | プロジェクト一覧を表示する | 「自分の Vercel プロジェクトを一覧表示して」 |
| `get_project` | プロジェクトの詳細を確認する | 「このプロジェクトの詳細を教えて」 |
| `list_teams` | チーム一覧を表示する | 「Vercel のチームを確認して」 |

**デバッグ・確認**

| ツール | できること | 指示の例 |
|--------|-----------|---------|
| `web_fetch_vercel_url` | デプロイ URL からコンテンツを取得する | 「本番の URL の内容を取得して」 |
| `get_access_to_vercel_url` | 保護されたデプロイへの一時リンクを生成する | 「プレビュー URL にアクセスできるリンクを作って」 |
| `search_documentation` | Vercel のドキュメントを検索する | 「Vercel の環境変数の設定方法を調べて」 |
| `check_domain_availability_and_price` | ドメインの空き状況と価格を確認する | 「example.com のドメインが取れるか調べて」 |

> **非エンジニアにとって何が嬉しいの？** 従来、デプロイをするには「ターミナルで正確なコマンドを打つ」か「ダッシュボードの正しい画面を探してボタンを押す」必要がありました。Vercel MCP を使えば、日本語で「デプロイして」と伝えるだけで完了します。エラーが出ても「原因を調べて直して」と依頼するだけで解決策を提示してくれます。

### 3-4. 環境変数の設定とデプロイの実行

**なぜ環境変数が必要か:**

ローカル環境では `.env.local` ファイルに Supabase の URL とキーを保存していました。しかし `.env.local` は Git に含まれていないため、Vercel のサーバーにはその情報が届きません。Vercel の「環境変数」機能を使って、本番サーバーにも同じ情報を安全に設定する必要があります。

> **環境変数って何？** アプリが動く「環境」ごとに変わる設定値のことです。「自分のパソコン」と「Vercel のサーバー」では環境が違うので、それぞれに別々に設定します。`.env.local` はメモ帳に書いた個人のメモ、Vercel の環境変数は会社の金庫に保管した公式な設定書類のイメージです。

必要な環境変数は以下の 2 つです。

```
NEXT_PUBLIC_SUPABASE_URL=https://xxxxxxxxxxxxxx.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJhbGciO...（長い文字列）
```

> **注意:** これらの値を第三者に教えないでください。特に `NEXT_PUBLIC_SUPABASE_ANON_KEY` は公開 API キーですが、Supabase の RLS（Chapter 4 で設定したセキュリティ機能）が有効であれば安全に使用できます。

**デプロイの実行:**

Claude Code に以下のように依頼します。

> Vercel にこのプロジェクトをデプロイして。GitHub リポジトリは `https://github.com/あなたのユーザー名/its_my_turn` で、.env.local の環境変数を設定して

Claude Code は以下の流れで作業を進めます。

1. `.env.local` の内容を読み取る
2. Vercel MCP の `deploy_to_vercel` ツールを呼び出す
3. GitHub リポジトリを Vercel に連携する
4. 環境変数（`NEXT_PUBLIC_SUPABASE_URL`、`NEXT_PUBLIC_SUPABASE_ANON_KEY`）を Vercel に設定する
5. デプロイを実行する

[screenshot: Claude Code が Vercel MCP のツールを呼び出してデプロイを実行している様子]

> **体験のポイント:** 従来は「Vercel ダッシュボードを開く → Import ボタンを押す → 環境変数を手入力する → Deploy ボタンを押す」という複数の手順が必要でした。Vercel MCP を使うと、これらをすべて Claude Code への一言で完了できます。

**デプロイが失敗した場合:**

Claude Code に原因の調査を依頼します。

> デプロイが失敗したみたい。ビルドログを確認して原因を調べて

Claude Code は Vercel MCP の `get_deployment_build_logs` ツールを使ってビルドログを自動取得し、エラーの原因と修正方法を提示してくれます。

> **ビルドログとは？** デプロイ中に何が起きているかを記録したメッセージの一覧です。うまくいけば最後に成功メッセージが表示されます。エラーが起きれば、ここに原因が書かれています。Vercel MCP がこの情報を自動で取得してくれるため、ダッシュボードを開く必要がありません。

[screenshot: Claude Code が Vercel MCP でビルドログを取得して原因を分析している様子]

### Step 3 の確認ポイント

- [ ] Vercel アカウントが作成されている
- [ ] `claude mcp list` で `vercel` が表示されている
- [ ] OAuth 認証が完了している
- [ ] `.env.local` に `NEXT_PUBLIC_SUPABASE_URL` と `NEXT_PUBLIC_SUPABASE_ANON_KEY` が存在する
- [ ] Vercel MCP 経由でデプロイが実行されている
- [ ] デプロイが成功している（Claude Code が公開 URL を報告する）
- [ ] 公開 URL（`https://プロジェクト名.vercel.app` のような形式）が発行されている

## Step 4: 本番動作確認 & 振り返り（20分）

このステップでは、公開されたアプリの動作を確認し、Supabase の設定を本番用に更新します。また、CI/CD の全体フローを体験して、チャプター全体の振り返りを行います。

### 4-1. 公開 URL でアプリを確認する

Claude Code が報告した公開 URL（`https://プロジェクト名.vercel.app`）をブラウザで開きます。

[screenshot: 公開 URL でブラウザに TODO アプリが表示されている様子]

以下のチェックリストで動作を確認します。

### 4-2. Supabase の本番用 URL を設定する（ダッシュボード操作）

Supabase の認証機能は、デフォルトで `localhost:3000`（自分のパソコン上のアドレス）からのアクセスのみ許可しています。本番の URL（`https://プロジェクト名.vercel.app`）を追加で登録する必要があります。

この作業は Supabase のダッシュボード上での手動操作が必要です。

> **なぜこの設定が必要なの？** セキュリティのためです。「どこからでも認証できる」状態にするのは危険なため、Supabase はあらかじめ「許可するアドレスのリスト」を持っています。本番 URL をそのリストに追加することで、本番環境からもログインできるようになります。

1. Supabase ダッシュボード（`https://supabase.com/dashboard`）を開く
2. プロジェクトを選択する
3. 左メニューの「Authentication」をクリックする
4. 「URL Configuration」を選択する

[screenshot: Supabase ダッシュボードの Authentication > URL Configuration 画面]

5. 「Site URL」を本番 URL に更新する:
   ```
   https://プロジェクト名.vercel.app
   ```

6. 「Redirect URLs」に以下を追加する（「Add URL」をクリック）:
   ```
   https://プロジェクト名.vercel.app/**
   ```

[screenshot: Supabase の Redirect URLs に本番 URL が追加された様子]

7. 「Save」をクリックして保存する

> **注意:** Site URL を変更すると、`localhost:3000` でのローカル開発時に認証が動作しなくなることがあります。ローカル開発の URL も Redirect URLs に残しておくことを推奨します:
> ```
> http://localhost:3000/**
> https://プロジェクト名.vercel.app/**
> ```

### 4-3. CI/CD の体験（push → テスト → デプロイ）

GitHub への push で「CI（テスト・ビルド）→ Vercel 自動デプロイ」が連続して動くことを体験します。

> **CI/CD とは？** Continuous Integration / Continuous Delivery の略です。「コードを push すると自動でテスト・ビルド・デプロイが走る仕組み」のことです。注文（push）するだけで自動的に届けてくれるデリバリーサービスのイメージです。一度設定すれば、毎回手動でデプロイする必要がなくなります。

**体験:** Claude Code に以下のように依頼してみましょう。

> TODO リストのスタイルを少し改善して、feature/style-tweak ブランチを作ってコミットして push して

Claude Code がコードを修正し、commit、push を行います。push 後に以下の 2 つが自動で動きます。

1. **GitHub Actions（CI）**: push を検知して lint → テスト → ビルドを自動実行
2. **Vercel**: GitHub への push を検知して自動デプロイ

GitHub のリポジトリ画面で「Actions」タブを開いて、CI が自動実行されていることを確認します。

[screenshot: GitHub Actions と Vercel の両方が自動で動いている様子]

Vercel MCP でデプロイの進捗を確認してみましょう。

> 最新のデプロイ状況を Vercel MCP で確認して

Claude Code が Vercel MCP の `list_deployments` ツールを使ってデプロイの進捗をリアルタイムで確認してくれます。

## トラブルシューティング

### テストが失敗する

テストを実行したが失敗（赤いエラー）が出た場合:

> テストが失敗しているので原因を調べて直して

Claude Code がエラーメッセージを分析して、テストコードまたはアプリコードの問題を特定し修正してくれます。

よくある原因:
- テストが古いコンポーネントの構造を前提にしている（コードを変更した後にテストが追いついていない）
- テスト環境の設定が不足している（Claude Code に「テスト設定を確認して」と依頼する）

---

### GitHub Actions が失敗する

GitHub の Actions タブでワークフローが失敗（赤い ×）になっている場合:

1. 失敗したワークフローをクリックする
2. どのステップで失敗しているかを確認する
3. Claude Code に失敗内容を共有して対処を依頼する

> GitHub Actions が失敗しています。エラーの内容は「（エラーメッセージ）」です。原因と修正方法を教えて

よくある原因:
- Node.js のバージョン不一致（ローカルと Actions の Node.js バージョンが違う）
- 環境変数が不足している（`NEXT_PUBLIC_SUPABASE_URL` などのシークレットが設定されていない）
- ローカルでは動いていたがテスト環境では動かない依存関係の問題

---

### ビルドエラーが出る

デプロイに失敗してビルドエラーが報告された場合、Claude Code に原因の調査を依頼します。

> デプロイが失敗しました。ビルドログを確認して原因と修正方法を教えて

Claude Code は Vercel MCP の `get_deployment_build_logs` ツールでログを自動取得して分析します。

ビルドエラーの原因として多いもの:

- TypeScript の型エラー（`any` を使っていないか確認）
- `process.env` の変数が undefined（環境変数名のスペルミス）
- Import パスのエラー（ファイルが存在しない、パスが間違っている）

> **TypeScript の型エラーとは？** TypeScript は「この変数には文字列しか入らないはず」という取り決めが厳しい言語です。取り決めに反したコードが含まれているとビルドが止まります。Claude Code に「型エラーを修正して」と伝えれば直してくれます。

ローカルでも確認したい場合は Claude Code に依頼します。

> ローカルでビルドを実行して、エラーが出たら修正して

---

### 環境変数が読み込まれない

Vercel にデプロイしてもアプリが Supabase に繋がらない場合、Claude Code に確認を依頼します。

> Vercel の環境変数が正しく設定されているか確認して。`NEXT_PUBLIC_SUPABASE_URL` と `NEXT_PUBLIC_SUPABASE_ANON_KEY` が設定されているはず

環境変数を修正した場合は再デプロイが必要です。

> 環境変数を修正したので、再デプロイして

よくある原因:

- 変数名に `NEXT_PUBLIC_` が付いていない（ブラウザから読める変数には必須）
- 値のコピーペースト時に余分なスペースが入った
- 環境変数を変更した後に再デプロイをしていない

---

### ランタイムエラーが起きる

デプロイは成功したのに「ページが真っ白」「機能が動かない」などの問題が起きた場合:

> 本番環境でランタイムエラーが起きているようです。ログを確認して原因を教えて

Claude Code は Vercel MCP の `get_runtime_logs` ツールでアプリケーションの実行ログを取得し、エラーの原因を分析します。

---

### Supabase の認証でリダイレクトエラーが出る

ログイン後に `Invalid redirect URL` のようなエラーが出る場合:

- Supabase ダッシュボード → 「Authentication」→「URL Configuration」を確認する
- 「Redirect URLs」に `https://プロジェクト名.vercel.app/**` が登録されているか確認する

> **「Invalid redirect URL」エラーとは？** 「このアドレスはリダイレクト先として許可されていません」というエラーです。Step 4-2 の設定を確認してください。

---

### GitHub への push が拒否される

```bash
# リモートリポジトリが登録されているか確認
git remote -v

# 登録されていない場合は追加する
git remote add origin https://github.com/あなたのユーザー名/リポジトリ名.git

# push する
git push -u origin main
```

認証エラーが出る場合は、GitHub の Personal Access Token（個人アクセストークン。GitHub を使うための鍵）が必要なことがあります。GitHub の設定画面（Settings → Developer settings → Personal access tokens）でトークンを生成してください。わからない場合はメンターに声をかけてください。

---

### Vercel MCP が動作しない

`vercel` が MCP リストに表示されない場合や、Vercel の操作が失敗する場合:

```bash
# MCP の設定を確認する
claude mcp list

# Vercel MCP が表示されない場合は追加する
claude mcp add --transport http vercel https://mcp.vercel.com
```

追加後、Claude Code を再起動してから再度試してください。認証が必要な場合はブラウザが自動で開きます。
