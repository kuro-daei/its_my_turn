# Module 6: 修正・改善 — Git ワークフロー

**所要時間**: 約 1.5 時間
**ゴール**: バグ修正や改善をブランチ運用で進める実務フローを体験する
**学ぶ Claude Code 機能**: コードレビュー、Git ブランチ運用、CLAUDE.md ルールの効果

---

## このモジュールで学ぶこと

- Claude Code にプロジェクト全体のコードをレビューしてもらい、問題点を洗い出す
- `fix/` ブランチでレビュー指摘に対応する
- `feature/` ブランチで UI 改善を加える
- CLAUDE.md のブランチルールが Claude Code の動作に反映されていることを確認する

---

このモジュールでは、「動いているアプリをさらに良くする」プロセスを体験します。

現実の開発では、「とりあえず動く状態」から「品質の高い状態」に磨き上げる作業が重要です。Git のブランチ運用を使うと、「本番には影響させずに安全に修正・改善できる」という強力な仕組みが機能します。

> **ブランチ（branch）って何？** 木の「枝」を意味します。本体（幹＝main ブランチ）から枝を分けて作業することで、本体に影響を与えずに試行錯誤できます。修正が完了したら枝を本体にマージ（合流）します。

Claude Code は単なるコード生成ツールではなく、**コードを読んで問題を見つけるレビュアー**としても機能します。このモジュールではその能力を最大限に活用します。

**3つのステップの流れ:**

```
Step 1: Claude Code にプロジェクト全体をレビューしてもらう（20分）
Step 2: fix/review-feedback ブランチで指摘事項を修正する  （40分）
Step 3: feature/ui-polish ブランチで改善を追加する        （30分）
```

間違えても大丈夫です。途中でわからなくなったら、すぐメンターに声をかけてください。

---

このモジュールを始める前に、以下の状態になっているか確認してください。

- [ ] 現在 `feature/initial-development` ブランチにいる

## Step 1: コードレビュー（20分）

### このステップの目的

Claude Code にプロジェクト全体のコードを読んでもらい、問題点や改善点を洗い出します。自分では気づきにくいセキュリティリスクやパフォーマンス問題を発見できます。

> **体験:** Claude Code は「コードを書く」だけでなく「コードを読んで評価する」こともできます。経験豊富なエンジニアが隣に座ってレビューしてくれるようなイメージです。

[screenshot: Claude Code のチャット画面にレビュー指示を入力した直後の様子]

### Claude Code への指示

Claude Code のチャット画面に、以下をそのまま入力してください。

> このプロジェクト全体をレビューして。改善点を以下の観点ごとに教えて:
> - パフォーマンス（表示速度、無駄な処理）
> - セキュリティ（情報漏洩リスク、入力値の検証）
> - 可読性（コードのわかりやすさ、命名）
> - エラーハンドリング（通信失敗、予期しない入力への対処）
> - アクセシビリティ（スクリーンリーダー対応、キーボード操作）
>
> 指摘事項は優先度（高・中・低）をつけてリストアップして

### Claude Code が返すレビューの例

Claude Code は以下のような形式でレビュー結果を返します（実際の内容はあなたのコードによって異なります）。

```
## コードレビュー結果

### パフォーマンス
[優先度: 中] TodoList コンポーネントで todos を毎回全件取得している。
フィルタリングに useMemo を使うと不要な再計算を防げる。

### セキュリティ
[優先度: 高] 環境変数 NEXT_PUBLIC_SUPABASE_ANON_KEY がクライアントサイドに
露出している。これ自体は設計通りだが、.env.local が .gitignore に
含まれているか確認が必要。

[優先度: 高] TODO テキストの入力値にサニタイズ処理がない。
XSS 対策として、入力値のトリムと長さ制限を追加するとよい。

### 可読性
[優先度: 低] TodoItem コンポーネントの props 名が item で汎用的すぎる。
todo に変更すると意図が明確になる。

### エラーハンドリング
[優先度: 高] Supabase との通信失敗時のエラー処理がない。
ネットワークエラーが発生した場合、ユーザーに何も表示されない状態になる。

### アクセシビリティ
[優先度: 中] チェックボックスに aria-label がない。
スクリーンリーダーで「チェックボックス」とだけ読まれてしまい、
どの TODO に対する操作なのかわからない。
```

> **XSS（クロスサイトスクリプティング）って何？** 悪意のある人が入力欄にプログラムコードを書き込んで、アプリを乗っ取ろうとする攻撃です。「入力値のサニタイズ（無害化）」を行うことで防げます。

> **アクセシビリティとは？** 目が不自由な人がスクリーンリーダー（画面の内容を読み上げるソフト）を使う場合でも、アプリを使いやすくする配慮のことです。

[screenshot: Claude Code のレビュー結果がチャット画面に表示されている様子。箇条書きで指摘事項が並んでいる]

### レビュー結果を整理する

Claude Code のレビュー結果が出たら、以下の確認を行います。

#### 確認ポイント

- [ ] レビュー結果が返ってきた
- [ ] 「優先度: 高」の指摘事項の件数を数えた
- [ ] どの指摘から対応するか自分の中で決めた

#### 優先度を決めるコツ

Claude Code への追加指示でさらに絞り込めます。

> 今のレビュー結果の中で、このモジュール（1.5時間）で対応すべき上位3件はどれか教えて

> **体験:** AI に「優先順位をつけて」と頼むことで、膨大なタスクを整理できます。コードに限らず、日常業務の整理にも使える Claude Code の強みです。

> **なぜ新しいブランチを作るの？** 修正が途中でうまくいかなくても、元のブランチに戻ればやり直せるからです。「下書き保存しながら作業する」イメージです。

```bash

```

#### または直接コマンドを実行（方法 B）

```bash
git checkout -b fix/review-feedback
```

#### ブランチ作成の確認

```bash
git branch --show-current
```

期待される出力:

```
fix/review-feedback
```

- [ ] `fix/review-feedback` ブランチにいることを確認した

> **体験:** CLAUDE.md にブランチ命名規則（`fix/`、`feature/` など）を書いておくと、Claude Code は自然にその命名規則に従ってブランチを作ります。設定を書いておくだけで人間が確認しなくてもルールが守られる仕組みです。

### 指摘事項を1件ずつ修正する

レビューで挙がった指摘事項を1件ずつ修正していきます。修正のたびにコミット（セーブポイントの記録）することが大切です。

#### 修正 1: エラーハンドリングの追加

Supabase との通信失敗時に何も表示されない問題を修正します。

> レビューで指摘された「Supabase 通信失敗時のエラーハンドリングがない」を修正して。
> 通信エラーが発生した場合、画面に「データの取得に失敗しました。再読み込みしてください。」というメッセージを表示して

Claude Code が修正コードを生成したら、ブラウザで動作確認します。

**確認方法（エラー状態を擬似的に再現する）:**

ネットワーク接続を一時的に切ってからページをリロードし、エラーメッセージが表示されるか確認します。確認後はネットワークを再接続してください。

確認ポイント:
- [ ] エラーメッセージがブラウザに表示される
- [ ] エラーメッセージのスタイルが読みやすい（赤背景など）
- [ ] 正常時はエラーメッセージが表示されない

確認できたらコミットします。

```bash
git add .
git commit -m "fix: add error handling for Supabase connection failure"
```

> **`fix:` プレフィックスとは？** Conventional Commits で「バグ修正」を意味します。`git log`（コミット履歴の確認）で見ると、修正と新機能が一目で区別できます。

---

#### 修正 2: 入力値のバリデーション追加

TODO テキストが空白のみ、または長すぎる場合の対処を追加します。

> レビューで指摘された「入力値のサニタイズ処理がない」を修正して。
> 具体的には以下の対応をして:
> - 空白のみのテキストでは TODO を追加できないようにする（入力欄を空にして警告を表示）
> - テキストが 200 文字を超えた場合は追加できないようにする（現在の文字数も表示して）

> **バリデーションとは？** 入力値の「検証」のことです。「ちゃんとした値が入っているか？」をチェックする処理です。空欄のまま送信されたり、極端に長いテキストが入力されたりするのを防ぎます。

確認ポイント:
- [ ] スペースだけ入力して「追加」を押してもリストに追加されない
- [ ] 201 文字以上の入力では「追加」ボタンが押せない、または警告が出る
- [ ] 文字数カウントが表示される（任意）

```bash
git add .
git commit -m "fix: add input validation for todo text (empty and max length)"
```

---

#### 修正 3: アクセシビリティの改善

チェックボックスに aria-label を追加し、スクリーンリーダーで内容がわかるようにします。

> チェックボックスにアクセシビリティ対応を追加して。
> 各 TODO アイテムのチェックボックスに aria-label を設定して。
> 内容は「[TODO のテキスト] を完了にする」という形式にして

> **`aria-label`（アリア ラベル）って何？** スクリーンリーダー（画面読み上げソフト）のために、見た目ではわからない情報を補う属性です。チェックボックスだけでは「何のチェックボックスか」がわかりませんが、`aria-label` を使うことで「買い物に行くを完了にする」と読み上げられるようになります。

確認ポイント:
- [ ] コード上で `aria-label` 属性が設定されている
- [ ] aria-label の内容に TODO のテキストが含まれている

```bash
git add .
git commit -m "fix: add aria-label to todo item checkboxes for accessibility"
```

## Step 3: 機能改善ブランチ（30分）

> **体験:** Claude Code は CLAUDE.md のブランチルールを読んでいます。「main ブランチでの commit/push は絶対禁止」というルールに従い、Claude Code は main ブランチへの切り替えに警告を出すか、代わりに適切なブランチ名を提案します。この動作が「CLAUDE.md がルールとして機能している」証拠です。ルールブックを書いておくだけで、自動的に守ってくれる仕組みです。

### 改善タスクを1件ずつ実装する

#### 改善 1: ローディング状態の追加

Supabase からデータを取得中であることをユーザーに伝えるローディング表示を追加します。

> TODO リストのデータ読み込み中にローディングスピナーを表示して。
> データ取得が完了したらスピナーを消して TODO リストを表示して。
> Tailwind CSS でシンプルなスピナーアニメーションを実装して

> **ローディングスピナーって何？** データの読み込み中に表示される「くるくる回るアイコン」のことです。ユーザーに「今処理中です。少し待ってください」と伝える役割があります。これがないと、画面が空白のまま固まったように見えてしまいます。

確認ポイント:
- [ ] ページを読み込んだ直後にスピナーが表示される
- [ ] 少し待つと TODO リストが表示される（スピナーが消える）
- [ ] スピナーのアニメーションが動いている

```bash
git add .
git commit -m "feat: add loading spinner while fetching todos"
```

> **`feat:` プレフィックスとは？** Conventional Commits で「新機能の追加」を意味します。`fix:`（問題を直す）と `feat:`（新しいものを加える）の使い分けを覚えておいてください。

---

#### 改善 2: UI の微調整（余白・色・フォントの統一）

全体的なビジュアルを整えます。

> 以下の UI の調整をして:
> - 各 TODO アイテムの上下の余白を少し広げて（現在より窮屈に見える）
> - 「追加」ボタンのホバー時の色変化を追加して
> - 完了済み TODO のテキストに打ち消し線を追加して、文字色を薄くして
> - TODO が 0 件のとき「TODO はまだありません」という空のステートメッセージを表示して

確認ポイント:
- [ ] TODO アイテムの間に適切な余白がある
- [ ] 「追加」ボタンにマウスを乗せると色が変わる
- [ ] 完了済み TODO は打ち消し線が入り、薄い色になっている
- [ ] TODO が 0 件のとき案内メッセージが表示される

```bash
git add .
git commit -m "style: improve todo item spacing and visual feedback"
```

> **`style:` プレフィックスとは？** Conventional Commits で「見た目（スタイル）のみの変更」を意味します。ロジック（処理の内容）は変えず、デザインだけを改善したときに使います。`feat:`、`fix:`、`style:`、`docs:`（ドキュメント変更）、`refactor:`（処理の書き直し）など、種類ごとにプレフィックスが決まっています。

#### 改善 3: ネットワークエラー時の表示強化

Step 2 で追加したエラーハンドリングをさらに改善します。

> TODO の追加・削除・完了切り替えが失敗したとき（ネットワークエラーなど）、
> 画面の上部にトースト通知（数秒後に消えるメッセージ）を表示して。

> **トースト通知って何？** パンのトーストが焼けて「ポップッ」と飛び出るように、画面の端に一瞬現れてすぐ消えるメッセージのことです。「TODO を追加しました」「削除に失敗しました」といった操作結果を、邪魔にならない形でユーザーに伝えます。

確認ポイント:
- [ ] TODO 追加が成功したとき緑のトーストが表示される
- [ ] トースト通知が 3〜5 秒後に自動で消える
- [ ] トースト通知のスタイルが画面に馴染んでいる（右上や下部に表示など）

```bash
git add .
git commit -m "feat: add toast notifications for CRUD operation feedback"
```

## `fix/` と `feature/` ブランチの使い分け

このモジュールで体験した 2 種類のブランチについて整理します。

| ブランチ種別 | 使うタイミング | コミットプレフィックス |
|---|---|---|
| `fix/` | バグ修正、レビュー指摘への対応 | `fix:` |
| `feature/` | 新機能追加、UI 改善、機能強化 | `feat:`、`style:`、`refactor:` |
| `docs/` | ドキュメント（README など）の変更 | `docs:` |
| `refactor/` | 動作を変えないコードの書き直し | `refactor:` |

> **体験:** ブランチの種類とコミットプレフィックスを合わせておくと、「このブランチは何のために作ったか」が名前だけで伝わります。チーム開発では特に重要で、他の人が見てもすぐに理解できます。

## うまくいかない場合

**Claude Code のレビューが薄い（「問題なし」と返ってくる）場合:**

もう少し具体的な観点を指定して再度依頼します。

> もう一度レビューして。特に `src/components/` 以下のすべてのファイルをひとつずつ確認して、エラーハンドリングが抜けているケースを全部リストアップして

**コミットメッセージで悩む場合:**

Claude Code に任せることができます。

> さっきの変更に適した Conventional Commits 形式のコミットメッセージを 3 案出して

**ブランチが増えて迷子になった場合:**

```bash
# 全ブランチを確認する
git branch

# 別のブランチに切り替える
git checkout fix/review-feedback
```

> **ブランチが増えすぎて混乱したら？** `git branch` で現在存在するブランチの一覧が表示されます。`*`（アスタリスク）が付いているのが今いるブランチです。わからなくなったらメンターに声をかけてください。
